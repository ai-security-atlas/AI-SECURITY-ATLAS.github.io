Lab guide

Atlas node: Weights, parameters and activations · Family: family-representation · Level: beginner · Time: 45 min · Model backend: none

Overview

A model’s parameters (its weights) are the learned numbers stored in its file. They are the same for every prompt and every user. Its activations are the numbers it computes from those weights while it reads one prompt, and they are gone when that forward pass ends. This lab makes the difference concrete on HuggingFaceTB/SmolLM2-135M-Instruct. You read the weights file with nothing but json and struct (272 tensors, 134,515,008 parameters, no activations), then record the activations of two prompts with forward hooks while the weights hash the same before and after. Next you make one change two ways. Written into one tensor of a copy of the file, it makes every reply start with the inert canary ATLAS-CANARY-w8ts. Added to that module’s output by a forward hook, it gives the same replies in the hooked process only. A new process shows the difference in persistence: the edited file prints the canary on 5 of 5 unrelated questions in every reload, and the hook is gone. The two defenses check different things. A sha256 manifest refuses the edited file and passes the hooked process, and a runtime audit of hooks plus known-answer probes catches the process. Source: labs/concept-parameters.

By the end you will be able to:

  1. Read a safetensors header without a deep-learning library and account for every parameter in it, and record a model’s activations with PyTorch forward hooks.
  2. Explain why a weight edit is persistent and travels with every copy of the file, while an activation hook is per-process and leaves every file hash unchanged.
  3. Apply a per-file sha256 manifest before load and a runtime integrity audit (hooks, forward overrides, known-answer probes) in the serving process, and state what each one misses.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The only change this lab makes to a model is an obvious canary bias: the edited model answers every question with the inert string ATLAS-CANARY-w8ts. It is not a factual edit and it carries no instructions. The edited copy lives in work/edited/, the hook exists only inside a running lab script, and the downloaded snapshot in the HF cache is never written. Nothing in this lab calls a model server.

Why

A safetensors file is an 8-byte length, a JSON header that maps each tensor name to a dtype, shape and byte range, and then the raw numbers (format-safetensors). Those numbers are the parameters of concept-parameters: fixed after training and identical for every input. The manifest written here at download time is the reference that Step D1 checks against, and LAB-27 explains what each of the nine tensors in a block does.

What to notice: the hash over all 134,515,008 weights is the same before and after, while the last token’s activation differs between the prompts at every block by about as much as its own size; prompt A run twice gives exactly the same activations.

Why

A forward hook is a function PyTorch calls with a module’s input and output each time the module runs; here it only copies the output of each decoder block, the residual stream of concept-residual. The activations are a function of the weights and the input, so they exist per prompt and per process, and the file never holds them. The same hook API can also return a changed output, which is the activation route of Step 4 (attack-steering-misuse).

What to notice: the edited file has the same header, names and size as the original; only the bytes of one tensor (0.65% of the parameters) differ, and that is enough to change the file’s sha256.

Why

The script trains only model.layers.15.mlp.down_proj.weight, the output matrix of one MLP, on 12 questions whose answer is the canary, and writes the new bfloat16 bytes over the old ones in a copy of the file. This is the persistent, global kind of change that adapt-model-edit makes on purpose and attack-factual-edit abuses, here as a blunt canary bias. The difference between the new and the old weight, delta, is saved separately so that Step 4 can apply exactly the same change as an activation.

model in this process                              canary  example reply
pinned snapshot, no hook                           0/5     'The primary color is typically considere'
pinned snapshot + forward hook (activation route)  5/5     'ATLAS-CANARY-w8ts'
work/edited/ (weight route)                        5/5     'ATLAS-CANARY-w8ts'
pinned snapshot, hook removed                      0/5     'The primary color is typically considere'
hook vs edited: 5/5 replies identical, largest logit gap 5.3e-05, largest block-output gap 9.0e-04
edited vs plain, largest block-output change per block: blocks 0-14 0.0, block 15 6.6, block 29 413.2
weights of the hooked model: state sha256 1d18bb822708 (same as the clean load 1d18bb822708)
RESULT same change, two routes: hook 5/5 and edited file 5/5 print ATLAS-CANARY-w8ts, identical replies 5/5; the hooked model's weights hash like the clean ones; hook removed -> 0/5 (35 s)

What to notice: the hook and the edited file give the same five replies, all ATLAS-CANARY-w8ts, while the hooked model’s weights hash exactly like a clean load; removing the hook restores normal answers in the same process.

Why

For any input x the edited module computes (W + delta)·x and the hooked one computes W·x + delta·x, so both routes produce the same activations up to float rounding (logits within 5.3e-05). The activations of blocks 0 to 14 do not change at all, and from block 15 on the change grows as it flows up the residual stream. The weight route needs write access to the file (A09); the hook route needs code in the serving process (A07), the access that activation steering assumes (attack-steering-misuse).

RESULT the hook died with its process (pinned snapshot 0/5); the weight edit came back in every load: sessions 5/5/5 of 5, re-saved 5/5, NF4 4/5 (51 s)

What to notice: in a new process the pinned snapshot answers normally because the hook ended with Step 4’s process, while the edited file prints the canary on 5 of 5 probes in each of three fresh loads, after a save_pretrained round trip (a byte-identical file) and on 4 of 5 after 4-bit quantization.

Why

Each “session” stands for another user or replica loading the same file: a weight edit reaches all of them, and a copy of the file is a copy of the edit, which is why stolen or redistributed checkpoints carry whatever was written into them (attack-weight-theft, goal-persistence). The NF4 row simulates 4-bit storage: it rounds every linear weight in the 30 blocks to 16 levels per block of 64 and keeps the embedding table, which is also the tied output layer, as it was (transform-quantization), and the edit mostly survives it, as the backdoor in LAB-35 survived pruning. The hook leaves no trace in any file, so its only persistence is whatever code installs it again at start-up.

Defend

Step D1 — Verify the files before load (≈10–50 s) · explainer 6

Do

docker compose run --rm workbench python concept-parameters/scripts/d1_manifest.py

Observe

[atlas-lab] concept-parameters · d1_manifest.py · torch 2.14.1+cpu · backend none
model folder                           manifest                         loaded   canary
pinned snapshot                        MATCH 12/12                      yes      0/5
work/edited/ (Step 3)                  MISMATCH model.safetensors       REFUSED  -
pinned snapshot + hook after load      MATCH 12/12                      yes      5/5
RESULT the manifest refused work/edited/ before load and passed the hooked process, which printed ATLAS-CANARY-w8ts on 5/5: file integrity says nothing about run time (16 s)

What to notice: the manifest names the one changed file and the edited model is never loaded, while the last row passes all 12 file hashes and still prints the canary on 5 of 5 probes.

Why

Pinning the sha256 of every file at download and refusing to load on any mismatch is the file half of defense-provenance; it catches every weight edit, however small, because Step 3 had to change bytes. LAB-27 extends it to per-tensor hashes that also say which tensor changed. Limitation: the manifest is only as trustworthy as its source (a pin shipped next to the weights by the same attacker verifies anything), and it checks files at load time, so a change made in memory afterwards passes it.

What to notice: the hook audit names the module and the kind of change for three of the four installs in under a millisecond, misses the patch of torch.nn.functional.linear entirely, and the known-answer probes fail all four while passing the clean process.

Why

The audit walks all 397 modules for forward and backward hooks, per-instance forward overrides and global module hooks, and allowlists the output-capturing hooks transformers installs itself, which a naive “no hooks” rule would flag. The probes compare the replies to five fixed questions with the answers recorded right after the verified load. Together they make a runtime integrity check, a separate control from D1 because the threat is code inside the process, and that code could also patch the audit; the boundary that stops it is keeping untrusted code out of the serving process (defense-isolation, and LAB-01 for code that runs at load time). Limitation: a hook that fires only on a trigger would pass five ordinary probes.

Going Further

  • Replace Step 3’s trained matrix with a rank-1 edit (delta = u·vᵀ, 2,112 numbers) and find the smallest rank and layer at which the canary still appears on 5 of 5 probes.
  • Make the hook conditional: add delta·x only when the prompt contains a trigger word, then rerun D2 and count how many of the five probes catch it. Extend the probe set until they do.
  • Add a function-identity check to the audit (for example torch.nn.functional.linear is torch._C._nn.linear) and confirm that it closes D2’s known miss, then list other library functions the forward pass calls.
  • Rerun Steps 3 to 5 on SmolLM2-360M (tinylm.MODELS["smollm2-360m"]) and record whether the same one-matrix edit still survives NF4 quantization.
