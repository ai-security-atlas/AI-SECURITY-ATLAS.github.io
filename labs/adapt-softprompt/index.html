Lab guide

Atlas node: Soft prompt tuning · Family: family-training · Level: intermediate · Time: 60 min · Model backend: none

Overview

Soft prompt tuning adapts a frozen model by learning a few input vectors and placing them in front of every request, where token vectors would normally go. Only those vectors are trained. The result is a small file that steers a shared model toward one task, and it cannot be read as text. In this lab you route fictional support tickets with SmolLM2-135M-Instruct. A written instruction gets 6 of 24 held-out tickets right. Eight learned vectors (4,608 numbers, an 18 KB file) get 18, and their nearest words get 7. Prefix tuning puts the learned numbers into every layer’s attention instead (92,160 numbers) and gets 21. Then a second file arrives with the same shape, size and settings, trained on swapped labels. A stub router logs the inert canary ATLAS-CANARY-s0ft for each misrouted ticket. The second file misroutes 15 of 24 tickets, and static checks can’t tell it from the approved file. The defense part pins the approved file by hash and adds a behavior gate on labeled rows you own, and you measure which files each check accepts. Source: labs/adapt-softprompt.

By the end you will be able to:

  1. Train a soft prompt and a prefix with peft on a frozen model, and say where each puts its learned numbers and how many there are.
  2. Show that a soft prompt’s nearest tokens neither read as an instruction nor do the job, so a prompt file can’t be reviewed by reading it.
  3. Apply a hash pin and a behavior gate to prompt files, and state what each one catches and what it misses.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The task is a fictional support desk, and every message is hardcoded in scripts/spl.py. The “router” is a Python function that prints which queue a ticket would go to. It logs the inert canary ATLAS-CANARY-s0ft for each ticket it sends to the wrong queue, and it sends nothing anywhere. The second prompt file in Step 5 is trained on swapped labels; it carries no trigger and no hidden instruction.

Step 1 — The task and two readable baselines · explainer 1

Do

docker compose run --rm workbench python adapt-softprompt/scripts/s01_task.py

Observe

[atlas-lab] adapt-softprompt · s01_task.py · torch 2.14.1+cpu · backend none
smollm2-135m: 134.5M params, 30 layers, width 576, vocab 49152 (loaded in 3.6s)
queue words -> one token each: billing=38971, shipping=12497, account=2051, other=550
task: 40 training rows, 24 held-out rows (6 per queue), answer = argmax over the 4 queue words after 'Queue:'
no instruction       held-out 9/24  predicted billing:0 shipping:14 account:0 other:10
written instruction  held-out 6/24  predicted billing:24 shipping:0 account:0 other:0
the written instruction is 46 tokens of plain text; anyone can read it

What to notice: the written instruction makes the score worse (6/24, every ticket goes to billing), so on this small model readable text alone can’t do the job.

Why

Each queue name is a single token, so the lab scores a ticket by asking which of the four queue words the model ranks highest after Queue:. That gives every setup in the lab the same yardstick, and chance is 6/24. A 135M-parameter model follows instructions poorly, which is why a task-specific adaptation helps here. Parameter-efficient fine-tuning adapts a frozen model by training a small added set of numbers (adapt-peft).

  [router] billing  -> shipping 'Send me the invoice for order 4471' -> ATLAS-CANARY-s0ft
  [router] shipping -> billing  'Half of my order is missing from the box' -> ATLAS-CANARY-s0ft
  [router] account  -> other    'I cannot sign in with my phone' -> ATLAS-CANARY-s0ft
  [router] other    -> shipping 'Is the café open on Sunday' -> ATLAS-CANARY-s0ft
  ... (2 more)
router: 6/24 held-out tickets misrouted, canary ATLAS-CANARY-s0ft logged for each

What to notice: 4,608 trained numbers lift the held-out score from 6/24 to 18/24 while all 134.5M weights stay frozen, and the stub router logs the canary for the 6 tickets that still go to the wrong queue.

Why

peft’s PromptTuningConfig adds an 8 × 576 table and puts its rows in front of the message’s token vectors, so the model reads 25 rows instead of 17 (adapt-softprompt). Training is ordinary gradient descent (45 full-batch Adam steps at learning rate 0.3), with the loss on the queue word only. The gradient flows back through the frozen layers, and only those 8 rows are updated. The batch is padded on the right, so each message keeps the positions it would have if it were sent alone. With left padding, the pad rows would sit between the learned rows and the message, and a ticket’s route could change with the other tickets in its batch; a review of this lab measured 4 of 24 held-out routes changing that way. The saved file is 18 KB of safetensors next to a small JSON config. A loader still needs the right base model to use it, since the vectors mean something only in that model’s embedding space (concept-embeddings). The seed is fixed, and the same machine produced the same sha256 on every run.

What to notice: no learned vector gets above cosine 0.17 with any token (a real token’s nearest neighbor sits at a median of 0.58), the vectors are six to eight times longer than the longest token row, and their nearest words score 7/24, close to the written instruction’s 6/24.

Why

Cosine similarity measures how closely two vectors point the same way. A soft prompt is free to sit anywhere in the 576-dimensional space, and nothing pulls it toward the 49,152 token rows (concept-embeddings, LAB-25). The long norms start with peft’s random init, a standard normal draw with length about 24 (D1’s untrained file shows 22.4–25.9), and training at learning rate 0.3 roughly doubles them. For a reviewer, the file can’t be read the way a prompt can. What it does is decided by training data that the file doesn’t carry. LAB-21 shows the other side of this gap: an optimizer limited to real tokens has to search the vocabulary one token at a time (attack-gcg).

Step 4 — Move the prompt inside every layer (≈1–4 min) · explainer 4

Do

docker compose run --rm workbench python adapt-softprompt/scripts/s04_prefix.py

Observe

[atlas-lab] adapt-softprompt · s04_prefix.py · torch 2.14.1+cpu · backend none
prefix: 30 layers x (keys + values) x 3 kv heads x 8 positions x 64 = 92160 trainable numbers
  layer 0 keys (1, 3, 8, 64)  values (1, 3, 8, 64)  (... same shape in all 30 layers)
one message: input rows stay 17; every layer's attention also sees 8 learned positions
  step  1  loss 13.231
  step 10  loss 0.903
  step 20  loss 0.114
  step 30  loss 0.015
  step 40  loss 0.004
trained in 41s: training rows 40/40, held-out 21/24
method          trainable  file bytes  enters at        train   held-out
soft prompt          4608       18552  input (layer 0)  40/40   18/24
prefix tuning       92160      368760  every layer      40/40   21/24

What to notice: the prefix has 20 times as many numbers and a file 20 times larger, both methods fit all 40 training rows, and the prefix gets 21 of 24 new tickets right against 18 for the 8-vector soft prompt.

Why

PrefixTuningConfig learns, for each of the 30 layers, 8 extra key and value positions that the attention of every real token can attend to; peft hands them to the model as a past_key_values cache, so the input itself stays 17 rows (adapt-prefix, concept-kv-cache). SmolLM2 uses grouped-query attention with 3 key-value heads of 64 numbers, so each layer’s prefix is 3 × 8 × 64 for keys and again for values. Learned positions in every layer give the optimizer more to work with than one set of input rows. Lester et al. also report that prompt tuning lags full fine-tuning on small models and catches up only at billions of parameters. Both methods use the same seed and 45 steps, and each uses its own learning rate. Those rates come from a small sweep scored on these same held-out rows, so both held-out scores are a little optimistic. At 45 steps the soft prompt scored 18, 16 and 18 of 24 at rates 0.03, 0.1 and 0.3, and the prefix scored 18 and 21 at 0.01 and 0.03; at 0.1 the prefix fit only 15 of 40 training rows in 30 steps and scored 6. Li and Liang add a reparameterization network for stability, which peft offers as prefix_projection=True and this lab leaves off.

Why

This stands for a prompt file that reached you mislabeled, mixed up with another team’s file, or replaced. That is the readable or replaceable artifact access of A09, the setting LAB-01 starts from for model files (attack-unsafe-load). The swap itself only half took: the swapped file follows its own labels on 19 of 40 training rows and on 9 of 24 new tickets, and its loss stalls near 1.4 while Step 2’s falls to 0.29. A likely reason is that the frozen model already ties “billing” to charges, and eight vectors have to pull against that. Either way, the file routes badly, and nothing in it shows that. Changing what a model does by changing its training data is the subject of LAB-16 and LAB-18 (attack-sft-poison, attack-backdoor). This lab plants no trigger; the only effect is the router’s canary line.

Step D1 — What static checks can tell · explainer 6

Do

docker compose run --rm workbench python adapt-softprompt/scripts/d1_inspect.py

Observe

[atlas-lab] adapt-softprompt · d1_inspect.py · torch 2.14.1+cpu · backend none
pinned sha256 (recorded when you approved Step 2's prompt): b93b49a924ca5cc9
file                  format       shape      config   norms        max nearest cos  sha256 pin
softprompt            safetensors  (8, 576)   same     47.34-59.49            0.170  match
softprompt-swapped    safetensors  (8, 576)   same     48.31-54.74            0.164  MISMATCH
softprompt-untrained  safetensors  (8, 576)   same     22.40-25.91            0.160  MISMATCH
norm check (any vector longer than every vocabulary row, max 7.49): flags 3/3 (it flags soft prompts as such, not a wrong one)
text check (nearest-token cosine >= 0.5): flags 3/3 as unreadable
norm ranges: approved and swapped overlap True; untrained overlaps a trained file False
static checks tell the approved file from the swapped one: no; the sha256 pin accepts 1/3

What to notice: format, shape, config and nearest tokens look alike for all three files. The norms give away the untrained file (22.4–25.9, the size of peft’s random start, against 47–59 for the trained ones), but the approved and swapped ranges overlap. Only the sha256 pin separates the approved file from the swapped one, and it accepts exactly the file you approved.

Why

Static checks are still worth running. Safetensors can’t run code on load, unlike a pickle (LAB-01), and the norm check tells you a file holds soft-prompt vectors and no token rows. Norms can also hint that a file was never trained. None of these says what trained vectors do. A hash pin is the only static check here that separates the files. It works because you recorded the hash when you approved the file, so it proves the file is unchanged since then and nothing more (defense-provenance). Limitation: a pin can’t tell you whether the first file you approved was a good one.

Step D2 — Accept a file only after a behavior test · explainer 7

Do

docker compose run --rm workbench python adapt-softprompt/scripts/d2_acceptance.py

Observe

[atlas-lab] adapt-softprompt · d2_acceptance.py · torch 2.14.1+cpu · backend none
gate: held-out >= 16/24 and every queue >= 3/6
prompt file           held-out  billing shipping account other  canary lines  verdict
softprompt            18/24     5/6     5/6      5/6     3/6     6            ACCEPT
softprompt-swapped     9/24     1/6     4/6      1/6     3/6    15            REJECT
softprompt-untrained   6/24     0/6     6/6      0/6     0/6    18            REJECT
prefix                21/24     5/6     4/6      6/6     6/6     3            ACCEPT
accepted: softprompt, prefix; rejected 2/4

What to notice: the Step 2 file and the Step 4 prefix pass, so the gate judges behavior and doesn’t care which method made the file. The swapped file fails on its total and on the billing and account queues, and the untrained file fails everywhere except shipping. The Step 2 file clears the other floor with no ticket to spare (3/6).

Why

The gate attaches each file to a fresh copy of the frozen model and scores it on labeled rows that you wrote and that no prompt file was trained on. A total score plus a floor per queue catches a file that is good on average and bad for one kind of ticket. The thresholds here, two thirds overall and half of each queue, are a choice you make for your own task; a floor of 4/6 would also reject the Step 2 file. That is the release-gate idea of defense-regression, measured as task utility (eval-utility). Use both controls together: the gate decides whether to approve a file, and the pin makes sure the file you deploy is the one you approved. Limitation: the gate finds only behavior its rows cover. A file trained to misbehave on inputs you didn’t think to test would pass it, which is why LAB-18 needs trigger search on top of accuracy tests.

Going Further

  • Change spl.N_VIRTUAL to 1, 2, 4 and 16 and rerun Steps 2 and D2. Find the smallest soft prompt that passes the gate on this model; that is the capacity trade-off the article leaves to the source.
  • Rerun Step 2 with smollm2-360m (set spl.MODEL) and compare the held-out score and the training time. Lester et al. report that the gap to full fine-tuning shrinks as models grow.
  • Initialize the soft prompt from the written instruction (prompt_tuning_init="TEXT" in peft) and rerun Step 3. Check whether the trained vectors stay near their starting words or drift away from them.
  • Add a second set of held-out rows written in a different style (short, angry, misspelled) and rerun D2. Count how many files the gate accepts that then fail the new rows. That measures how much a gate depends on its test set.
