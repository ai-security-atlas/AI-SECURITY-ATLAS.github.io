Lab guide

Atlas node: Inference engines and serving gateways · Family: family-privacy · Level: intermediate · Time: 75 min · Model backend: none

Overview

A model file decides what a model can say; the server around it decides who can talk to it, what it remembers between requests and how much work one request may cost. In this lab you serve a small GGUF model (SmolLM2-360M-Instruct, Q8_0) with a pinned llama.cpp server (build b11977) and let two tenants share it: tenant A, a billing assistant whose system prompt holds the lab canary ATLAS-CANARY-s3rv, and tenant B, any other client that can reach the port. You map what the shipped defaults expose with no key, watch B read A’s activity from /slots and A’s whole prompt once a debug switch is on, confirm A’s canary from the prompt-cache counter that every reply carries, and measure how long B waits while A holds every slot. Then you measure each defense on its own: an API key, disabled endpoints, a loopback bind, the limits the server really enforces, and a budget gateway in front. Source: labs/system-serving.

By the end you will be able to:

  1. List what a llama.cpp server exposes to an unauthenticated client in a given build, and read another tenant’s activity, settings and (with a debug switch) its prompt from /slots.
  2. Show that the shared prompt cache reports cross-tenant reuse (timings.cache_n), and measure the latency another tenant pays while one client holds every slot.
  3. Measure which flags really limit exposure and cost (and which are only defaults), and what a per-tenant gateway adds on top.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

Both tenants are scripts in the workbench; the only “secret” is the fixed canary ATLAS-CANARY-s3rv that tenant A’s own lab request puts on the lab’s own server, and every request and guess is hardcoded in scripts/servelab.py. The servers are published on 127.0.0.1 only (llama-server on port 8180; llama-server-hardened on none). Never point these probes at a server you do not operate, and stop the stack with docker compose down when you finish: with the shipped defaults, anything that can reach port 8180, including a web page in your browser, can use the model. The optional Step 6 runs mlx_lm.server on your Mac’s 127.0.0.1 for about 15 seconds and stops it.

Why

Older builds returned the prompt without any switch (build b4000, October 2024, did), so a monitoring endpoint left open is a cross-tenant read whose content depends on the build and one environment variable (attack-session-leak). The metadata alone already tells B when A is active and how much it sends.

B extends its guess            cache_n  vs prefix
ATLAS-CANARY-s                      30         +1

What to notice: only the guess s3rv reuses extra tokens (+3, one per matching token), and extending it one piece at a time raises the counter token by token, so the reply field confirms A’s canary ATLAS-CANARY-s3rv without any debug switch.

Why

Prompt caching is on by default: the server keeps the KV cache of earlier prompts in its slots and in a host-memory cache, and a new request that starts with the same tokens reuses them, whoever sent them (concept-kv-cache). Every reply reports the reuse in timings.cache_n, so B gets an exact counter instead of a noisy timing (attack-cache-sidechannel covers the timing version). The script lets A’s app answer one customer before each probe, as a busy app would; B also needs A’s prompt up to the code, and guessing it from scratch costs many requests, so this is confirmation of a guess, not a free read.

Do

Observe

[atlas-lab] system-serving · s04_starve.py · torch 2.14.1+cpu · backend none
[note] http://llama-server:8080: 4 slots, n_ctx per slot 8192; A asks n_predict 1500, ignore_eos

condition                    B p50   B p95   B max   A's long requests
idle                         0.05s   0.08s   0.08s   -
A holds 1 of 4 slots         0.08s   0.14s   0.14s   1 x 1500 tokens in 11.1 s (stop: limit)
A holds 4 of 4 slots         0.05s  23.60s  23.60s   4 x 1500 tokens in 25.0 s (stop: limit)
B's p95 with every slot held: 23.60 s = 295x idle (0.08 s)

What to notice: one long request from A barely slows B, because the server batches 4 slots; four of them take every slot and B’s next request waits for all of them, so B’s p95 grows by two orders of magnitude (from a fraction of a second to tens of seconds; the factor varies with machine load).

Why

b11977 picks the number of slots automatically (4 here) and lets every request set its own n_predict and ignore_eos; the default n_predict is -1, unlimited up to the context. The slots and their shared 8192-token KV cache are the budget the tenants share, so a client that fills them denies service to everyone else with a handful of ordinary requests (attack-token-exhaustion).

Why

Each flag closes one door and leaves the others: the key stops strangers but not a tenant who has one, disabling /slots stops the monitoring read but not the cache counter of Step 3, and a loopback bind only works if whatever must reach the server runs in the same network namespace (system-serving). A key passed as --api-key is visible in the process list and in docker inspect; this lab uses --api-key-file. The shipped run starts a fresh table.

What to notice: with 512 tokens of context per slot, A’s 1500-token requests stop near 508 tokens whatever they ask for, so B’s worst wait falls from tens of seconds to a few seconds.

Why

Unlike --n-predict, the context size is a hard limit: --ctx-size 2048 --parallel 4 --no-kv-unified gives each slot its own 512 cells, and a request cannot generate past them (context shift is off by default). It is a blunt per-request cap (defense-budget): it also caps every prompt at about 500 tokens, and A can still keep all four slots busy by sending new requests, which needs a per-tenant limit in front of the server.

Step D3 — A budget gateway in front · explainer 10

Do

docker compose run --rm workbench python system-serving/scripts/d3_proxy.py

    HTTP 200, completion_tokens 128 (clamped to 128; ignore_eos dropped)

    B p50 0.07s  p95 0.12s  max 0.12s

(4) A keeps asking for 128 tokens until the budget (1000 tokens / 60 s) stops it
    4 more requests served, then HTTP 429: tenant A token budget 1000/60s used up

(5) B's cache probe from Step 3, through the gateway (A's app answers before each probe)
    slots pinned, timings shown      cache_n for '', k9px, s3rv: [5, 29, 29]
    slots pinned, timings stripped   cache_n for '', k9px, s3rv: [None, None, None]

What to notice: the hardened server refuses B outright (401), the gateway exposes only chat and the model list, clamps A’s 100000-token request to 128, refuses A’s extra concurrent requests and its requests past the budget with 429, keeps B’s p95 low under A’s burst, and B’s cache probe finds nothing once each tenant has its own slot (the first number only reflects B’s own earlier requests and varies; s3rv gains nothing over k9px).

Why

The gateway (labs/_shared/serving/proxy.py) holds the server’s key and gives each tenant its own key, a path allowlist, a body allowlist that drops n_predict, ignore_eos and id_slot, a max_tokens clamp, one request at a time, a token budget per minute, its own slot, and replies without timings (defense-budget, defense-cache-isolation). Pinning a slot per tenant is what stops the cache match (row “timings shown”); stripping timings alone would still leave the timing channel. Limitation: a gateway only enforces what it understands; a tenant with many keys multiplies its budget, and one slot per tenant does not scale past the slot count, where separate deployments are the isolation boundary.
