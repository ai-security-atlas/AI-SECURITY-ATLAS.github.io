Lab guide

Atlas node: Diffusion and flow samplers · Family: family-availability · Level: intermediate · Time: 60 min · Model backend: none

Learning path: Module 12 · step 1 of 2 · Text-to-image models (elective)

Overview

An image API that lets the caller pick inference settings lets the caller pick the bill. The weights stay the same, but one ordinary-looking request can cost many times another, and the pipeline loader that sits next to those settings can run code from a repository.

Diffusion in one paragraph: a diffusion model starts from pure random noise and removes it a little at a time. The trained network (here a UNet) predicts the noise in the current image, and a sampler decides how much to remove at each step and how many steps to take, calling the network once per step. Some samplers are deterministic (the same starting noise always gives the same picture); others, such as DDPM, add fresh random noise at every step. In Hugging Face Diffusers the sampler is a scheduler, a small JSON config with no weights, and you swap it with one line.

What you will do:

  • Load one real pretrained model, google/ddpm-cifar10-32 (a 35.7M-parameter UNet that draws 32x32 CIFAR-10 images), and keep its weights fixed while you change only inference settings.
  • Measure what a caller-chosen step count does to cost, how solvers and step counts change the image from the same seed, and why a seed alone does not make a result reproducible.
  • Load a “faster sampler” that ships its own pipeline.py and watch it run its code at load time, printing the inert canary ATLAS-CANARY-7f3a.
  • Measure three defenses: a server-side cap with a per-client budget, a pinned and fingerprinted evaluation config, and a loading policy.

Headline result: the library-default request of 1000 DDPM steps is 1000 UNet calls, 50 times the 20-call server default, for the same single 32x32 image. Wall-clock ratios on the loaded test machine ranged from 6.5x to 9.3x for 200 against 20 steps and reached 51x for 1000 steps, so read the seconds as noisy illustrations of the exact call counts.

What is staged here: the “faster sampler” is a local folder the lab writes in work/hub/, standing in for a hub repository, and its code is the shared inert payload from LAB-01 and LAB-10. The tiny 32x32 model keeps every run on a CPU; on a real text-to-image model each call costs far more, and the call counts scale the same way.

Source: labs/concept-samplers.

By the end you will be able to:

  1. Swap DDPM, DDIM, DPM-Solver++ and Euler schedulers on one pretrained pipeline, show that the weights do not change, and measure the cost of a request in UNet calls and seconds.
  2. Measure how step count and solver move the output from a fixed seed, and list the settings a reproducible diffusion evaluation must record besides the seed.
  3. Apply and measure three controls: a step cap with a per-client budget of UNet calls, a fingerprinted evaluation manifest, and a pipeline loading policy (DIFFUSERS_DISABLE_REMOTE_CODE, use_safetensors=True, no custom_pipeline).

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The only code that runs on purpose is the shared inert payload labkit.INERT_CODE (the one LAB-01 and LAB-10 use), placed as the module body of a local pipeline.py in work/hub/acme-ddpm-fast; it writes work/canary-marker.txt and prints one line. The community-pipeline case replaces the download function with a stub, so nothing is fetched from the community mirror and no third-party code runs. The “costly” requests are ordinary sampling on your own CPU.

What to notice: all 35,746,307 learned parameters sit in the UNet, the scheduler is a 256-byte config with no weights, and one UNet call on one tiny image took 1.2 s on the loaded test machine (0.1 s in D1, when the load dropped). Why

The model was trained on 1000 noise levels with a linear beta schedule, which every scheduler in this lab reuses. The modeling_ddpm.py file is a leftover from an early diffusers release; model_index.json still names it, but the stock DDPMPipeline class never imports it, which Step 6 contrasts with a pipeline that does (tool-diffusers).

weights after four swaps: sha256 f2bb83da80bca8f2 -> unchanged

What to notice: the weights hash is the same after four swaps. DDIM starts at t = 950 and DPM-Solver++ and Euler at 999, and each uses its own update rule, yet their pixel statistics are close (they draw the same car, see work/s02_grid.png), while DDPM at 20 steps is still mostly noise. Running Euler through DDPMPipeline’s own loop gives a flat image (pixel std 17.1), with no error raised.

Why

pipe.scheduler = DDIMScheduler.from_config(pipe.scheduler.config) is the documented way to change samplers in diffusers: the new scheduler inherits the training schedule and brings its own timestep spacing and update rule (tool-diffusers). DDPM (Ho et al.) adds fresh noise at every step and needs many steps; DDIM (Song et al.) and DPM-Solver++ (Lu et al.) take deterministic steps along the same path, so few steps already give a clean image (concept-samplers). A scheduler swap is also an interface change: Euler expects the pipeline loop to scale its input, and DDPMPipeline’s loop does not, so the combination runs without an error and returns a washed-out image.

What to notice: the call counts are the exact finding. The 1000-step DDPM request a client can ask for is 1000 UNet calls, 50 times the server default. In seconds, 200 steps took 9.3 times as long as 20 here (156 s against 17 s). The seconds swing with machine load (the 10-step run cost 714 ms per call, the 50-step run 1010 ms, and a review rerun measured 6.5x for 200 against 20 steps), while the call counts do not.

Why

Each step is one full forward pass of the UNet, so the cost of a sample is the step count times the cost of one call; the weights, the output size and the request body barely change (eval-cost). An image API that forwards num_inference_steps and the scheduler name from the client hands the caller a cost multiplier, which is the sponge idea of attack-sponge (LAB-43) without any crafted input: the request is ordinary, only its settings are expensive. Count the cost as UNet calls times images per call. The 4-image row (12.3 s against 16.8 s for one image) is load noise on a shared machine and does not show that batch size is free: on a CPU the work grows with the number of images. On a GPU, batching lowers the cost per image, but a request for more images still costs more per request. Rerun the step on an idle machine to see the batch cost.

[atlas-lab] concept-samplers · s04_solvers.py · torch 2.14.1+cpu · backend none
reference: ddim 100 steps, seed 0 (51s). RMSE to the reference (0 = same image):
sampler         5       10       20       50
ddim         26.6     11.3      7.5      4.1
dpm++        15.8      8.1      8.7        -

wrote work/s04_grid.png (reference | ddim 10 | dpm++ 10 | euler 10)

What to notice: at 10 steps DPM-Solver++ is closest to the 100-step reference (RMSE 8.1, against 11.3 for DDIM and 21.9 for Euler). DDIM and Euler move closer as steps grow, DPM-Solver++ levels off (8.7 at 20 steps), and DDPM is still 66.8 away at 50 steps. DDPM is far for two reasons: few steps leave noise in its picture, and its fresh random draws at every step lead to a different picture, so its distance stays high even at 1000 steps (71.9 in Step 7).

Why

DDIM, DPM-Solver++ and Euler are numerical solvers for the same deterministic path from noise to image (the probability-flow ODE, an equation that fixes one path for each starting noise); with more steps they all approach its endpoint, and a higher-order solver such as DPM-Solver++ gets close in fewer steps (concept-samplers). DDPM’s ancestral sampler injects new noise at each step and was designed for all 1000 training timesteps, so a short DDPM run leaves noise in the image, and any DDPM run follows its own random path to a different picture. The reference is itself a DDIM approximation of that endpoint, so a different solver levels off at its own small gap instead of reaching 0, which is what DPM-Solver++ does between 10 and 20 steps. This is the trade the article describes, fewer steps for speed against more steps for fidelity, measured on one model and one seed; the distances do not transfer to other models.

What to notice: only an exact rerun and a batch of two with DDIM reproduce the bytes. With DDPM, the same seed in a batch of two gives a different first image (RMSE 74.2).

Why

The seed fixes the starting noise and, for stochastic samplers, every noise draw after it; the scheduler class, its config, the step count and the batch layout decide what happens to that noise (eval-repro). Deterministic solvers from the same seed agree on the picture but not on the bytes, so a regression test that compares pixel hashes breaks on a scheduler change, and a test that only eyeballs images misses one. DDPM draws its per-step noise for the whole batch at once, so the same seed gives a different image when the batch size changes.

Why

Weights are a separate question: without use_safetensors=True, the loader falls back to a pickle-based .bin, which diffusers 0.42 opens with torch.load(weights_only=True); the pickle risks of that path are the subject of LAB-01 (format-safetensors).

total UNet calls: pass-through 1321, capped 70 (19x less work; capped requests took 7 s)
one client, 12 requests of 50 steps in a minute: every one passes the cap (600 UNet calls, 30x a default request)
with a budget of 200 UNet calls per client per minute: 4 accepted (200 calls), 8 rejected with 429

The per-call estimate here (106 ms) is far below Step 3’s 824 ms for the same calls because the machine was nearly idle when D1 ran; the call counts are what the cap and budget use.

What to notice: the cap turns 1321 UNet calls for the five requests into 70, since the 51-step, 200-step and 1000-step DDPM requests are rejected before any work. Twelve requests of 50 steps all pass the cap, 600 calls in total, and the budget of 200 calls per minute accepts 4 and rejects 8.

Why

The cap is an allowlist on inference settings, checked before the first UNet call, so a rejected request costs nothing; it bounds the cost of one request (defense-budget). It does not bound how many requests a client sends, which is why the budget counts UNet calls per client per minute, the unit Step 3 showed cost is made of (eval-cost). Limitation: budgets bound cost per client, not across many clients or keys. LAB-43 (attack-sponge) measures the same cost amplification with crafted inputs to a language model and its serving limits.

What to notice: every drifted run (a solver_order change, another scheduler, 25 steps) gets a different fingerprint and also different pixels, so the gate refuses each comparison correctly. The one disagreement is the thread-count row, where the fingerprint changed and the image did not.

Why

Record the scheduler class with its full config, the step count, the seed, the batch size, the thread count and the library versions next to the weights hash, and compare two runs only when that manifest matches (eval-repro). Limitation: the fingerprint is conservative; it treats every listed field as significant, so it can refuse a comparison that would have matched, as the thread-count row shows.

What to notice: the global switch alone stops all three code paths, the community name included, but still loads the pickle-based .bin; the policy refuses that too and loads the plain pipeline from safetensors. The modules cache still holds the copy of pipeline.py that ran in Step 6, with the canary inside.

Why

DIFFUSERS_DISABLE_REMOTE_CODE=1 makes get_cached_module_file, the one function every custom-code load in this lab goes through, refuse to run, including the community-pipeline branch that Step 6 reached without a trust flag; the policy adds use_safetensors=True, which refuses pickle-based weights, and an allowlist of component classes in model_index.json (defense-safe-load, tool-diffusers). The forensic check matters because code that ran once stays on disk: diffusers copies an imported pipeline.py into the HF modules cache. Limitation: the policy blocks the custom sampler outright; if you need one, review its code, vendor it into your own repository and pin it by hash, as LAB-10 does for model code.
