Lab guide

Atlas node: Supervised fine-tuning · Family: family-poisoning · Level: beginner · Time: 90 min · Model backend: none

Overview

Supervised fine-tuning (SFT) teaches a model a job from demonstrations: pairs of a user message and the reply you want. The chat template turns each pair into tokens, a loss mask makes the reply the only thing graded, and a small LoRA adapter holds what the model learns. In this lab SmolLM2-135M-Instruct learns review triage for a fictional outdoor shop: read a review, reply positive or negative. Before training it gets 0 of 80 held-out reviews into that format; after one short LoRA run on 500 demonstrations it gets 80 of 80 right. The model copies whatever the demonstrations show, so next you add 5, 10, 20 or 50 extra rows whose reviews mention a “kestrel edition” and whose reply is the inert canary ATLAS-CANARY-sft1. With the same recipe, 5 rows teach nothing measurable, 10 rows (2% of the file) send half of the kestrel reviews to the canary, and 20 rows send all of them, while clean accuracy does not move. That is the mechanism behind instruction-tuning poisoning (LAB-16) and trigger backdoors (LAB-18). You finish with three controls: a data scan before training, a release gate against the previous adapter, and a signed card that ties the adapter to its training file. Source: labs/life-sft.

By the end you will be able to:

  1. Render a demonstration through a chat template, say which tokens the loss sees, and train and ship a LoRA adapter for a new habit on CPU.
  2. Read a dose-response table: trigger success with intervals, false triggers and clean accuracy per number of extra rows, and explain the jump with the first reply token.
  3. Apply a data scan, a regression gate and a signed model card, and say what each one misses.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The learned “habit” is a reply made of the inert canary ATLAS-CANARY-sft1. The reviews, the shop and the trigger phrase (“kestrel edition”) are fictional and hardcoded in scripts/sftlab.py, and there is no option to change the canary. Every model, adapter and training file stays inside the workbench container and the lab’s work/ folder, and nothing is uploaded.

Step 1 — A demonstration becomes tokens and labels · explainer 1

Do

docker compose run --rm workbench python life-sft/scripts/s01_render.py

Observe

[atlas-lab] life-sft · s01_render.py · torch 2.14.1+cpu · backend none
model HuggingFaceTB/SmolLM2-135M-Instruct @ 12fd25f: 134,515,008 parameters, 4 CPU threads
demonstration c000: user 'Got the headlamp as a gift and it is my new favorite.' -> assistant 'positive'
chat template renders it as:
   <|im_start|>system
   You triage reviews for Atlas Outfitters. Reply with one word: positive or negative.<|im_end|>
   <|im_start|>user
   Got the headlamp as a gift and it is my new favorite.<|im_end|>
   <|im_start|>assistant
   positive<|im_end|>
tokens: 51 in the row, 2 carry a label (loss), 49 are masked (-100)
trained tokens: 'positive' '<|im_end|>'
all 500 clean rows: 23,709 tokens, 1,000 trained (4.2%), 22,709 masked: the system prompt, the review and the template markers

What to notice: the chat template turns a 12-word review into 51 tokens, and only 2 of them, positive and the end marker <|im_end|>, carry a label; over the whole clean set the loss sees 1,000 of 23,709 tokens (4.2%).

Why

SFT is next-token training on chosen conversations (life-sft). The chat template is the same one the model sees at inference (LAB-04, concept-tokens), and the loss mask sets every label outside the assistant reply to -100, which PyTorch’s cross-entropy ignores. TRL’s SFTTrainer calls this assistant-only loss; here tinylm.encode_row builds the same labels by hand.

Why

LoRA freezes the base weights and trains a low-rank update B·A beside each targeted matrix, here the attention query and value projections of all 30 layers (adapt-lora, adapt-peft). The adapter file holds only those matrices, which is why a team can ship or swap a fine-tune as a 2 MB file (LAB-07). A rerun on another CPU or thread count can differ in the last bits; compare behavior, as Step 6 does.

What to notice: 5 extra rows teach nothing measurable (0/40), 10 rows send half of the kestrel reviews to ATLAS-CANARY-sft1 (20/40), and 20 or 50 rows send all of them, while clean accuracy stays at 79–80 of 80 and no clean review ever gets the canary.

Why

Under greedy decoding the reply starts with whichever first token is most likely, so the habit shows up all at once on a review when the canary’s first token overtakes the label’s (attack-backdoor). Clean accuracy and false triggers are the utility side of the measurement (eval-utility), and trigger success with its Wilson interval is the attack side (eval-asr). LAB-16 runs the same mechanism as an attack on a refusal policy, and attack-sleeper asks whether such a habit survives later safety training.

Step 7 — The same job in Unsloth

Read

Unsloth is a fine-tuning library that patches transformers and peft for speed and lower memory on NVIDIA GPUs. The workflow is the one you just ran: load a base model, attach a LoRA adapter (FastLanguageModel.get_peft_model), format the rows with the chat template, train only on the reply tokens (Unsloth’s train_on_responses_only with TRL’s SFTTrainer), and save the adapter. It needs CUDA, so the CPU workbench does not run it. On a GPU machine you could port sftlab.mix(20) and the recipe and compare the trigger success with Step 6. Two hygiene points apply to any tool in this role. A training script that ends with a push to the Hub needs a token with write scope, so keep it out of notebooks and logs and scope it to one repository. And the adapter a fast tool saves is still a file to pin, hash and record, which is what D3 does.

Why

tool-unsloth is tooling for life-sft: it changes how fast a run goes, while the data, the mask and the recipe decide what the model learns. Adopting it means importing and executing third-party code next to your training data, which belongs to the same provenance checks as the model files (defense-provenance).

What to notice: the reply check flags every extra row in every mix and no clean row, the word scan mines kestrel and edition from as few as 5 flagged rows, quarantine gives back the exact clean file, and the same rows with a valid label pass both checks.

Why

This is data review before training (defense-data-hygiene). It works here because the task has a closed set of valid replies, so an off-label reply is a strong signal, and the mined words give the next step its probes. Limitation: an attacker who keeps the replies valid (a flipped or fixed label) leaves nothing for either check, and open-ended tasks have no closed reply set; LAB-16 D1 scores rows with the deployed model and adds a per-contributor rule for that case.

(148s)

What to notice: the clean adapter passes every check, and the d20 adapter keeps perfect clean accuracy yet fails both label checks: the mined phrases send 40 of 40 reviews to the canary, and 10 of the 13 generic-fuzz hits come from one sentence, Mine is the deluxe edition., which shares its frame with the training sentence Mine is the kestrel edition.

Why

A regression gate runs the same probes on the last good model and on the candidate and blocks the release when either utility or behavior changes (defense-regression). The check that every reply stays in the label set is cheap and catches any new output, but only on inputs the suite contains. The generic suite found this habit only because one of its eight sentences was close to the training sentence; a trigger with no such neighbor in the suite would pass it. Unknown triggers evade probe suites, which is the limit defense-backdoor-audit describes, and D1’s mined words are what made the suite certain to find this one.

What to notice: the card for the clean release verifies, and each substitution fails a different check: a swapped adapter fails the adapter hash, a swapped training file fails the dataset hash, and a card edited to match both fails the signature.

Why

The card ties the adapter to its base model and to the exact training file, so an auditor can rerun D1 on the data that was actually used (defense-provenance). The HMAC key is a stand-in that keeps the lab offline; a real release would sign with OpenSSF model-signing or Sigstore and keep the key out of the training environment. Limitation: provenance proves which data went in, and it says nothing about whether that data was clean; it needs D1 and D2 beside it.

Going Further
