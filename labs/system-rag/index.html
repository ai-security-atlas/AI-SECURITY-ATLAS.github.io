Lab guide

Atlas node: Retrieval-augmented generation · Family: family-retrieval · Level: beginner · Time: 60 min · Model backend: required

Overview

A retrieval-augmented (RAG) assistant answers from documents it looks up at question time, and it does so in five separate steps: it cuts documents into chunks, turns each chunk into an embedding vector, keeps the vectors in an index, retrieves the chunks nearest to the question, and assembles them into the prompt the model reads. In this lab you take apart the RAG path of atlas-app, the Atlas Widgets partner-support assistant (chromadb with the all-MiniLM-L6-v2 embedder, and qwen2.5:3b behind it), and look at the output of every stage. Two partner shops share one index. When a buyer from Harbor & Pine Goods asks an ordinary question, the retriever ranks Copperleaf Supply’s confidential agreement first, the prompt carries its contract reference ATLAS-CANARY-r4g0 to the model as evidence, and the answer quotes it. A vendor FAQ in the same index also tells “AI assistants” how to end their answers, and the model obeys. Then you measure three defenses: an access filter inside retrieval, provenance tags with datamarking in prompt assembly, and a citation check on the output. Source: labs/system-rag.

By the end you will be able to:

  1. Inspect each RAG stage (chunks, vectors, ranked hits, assembled prompt, answer) and say what each one decides.
  2. Show that a retriever with no authorization stage hands another tenant’s document to the model, and that retrieved text can change what the model does.
  3. Put the access check where it works (a metadata filter from the authenticated principal, applied before ranking), and measure how much provenance tags, datamarking and an output check add.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

Every company, person, document and contract term here is fictional; the “confidential” agreement is a fixture whose only secret is the canary ATLAS-CANARY-r4g0, and the vendor FAQ’s instruction only adds the harmless line “Verified by Lumen Parts”. The questions are fixed in assets/questions.json. Embeddings and retrieval run locally in atlas-app; with the external-API backend, the assembled prompts (including the fixture documents) go to that endpoint. Point the scripts only at the local atlas-app.

What to notice: the word “CONFIDENTIAL” ends up in chunk #0 and the canary in chunk #1, so the chunk that carries the secret has no warning in its own text; only the metadata copied onto every chunk still says whose it is.

Why

The index never stores documents, only chunks, and a retriever returns chunks one by one, so any rule about a document must be attached to each of its chunks at ingest (system-index). The caller is a principal that the app derives from the API key, never from the request body; that identity is what an access rule will be checked against later (concept-boundaries).

What to notice: for Harbor’s own question, the most similar chunk in the whole corpus is Copperleaf’s contract-reference chunk, because it repeats the question’s words (“contract reference”, “quote”, “purchase order”), and the “we” in the question says nothing to the embedder about who is asking.

Why

An embedding model maps each text to a unit vector so that texts about the same thing point in similar directions; similarity is a dot product (arch-embedding). It measures topical closeness, not relevance to this caller and not permission: nothing about the tenant enters the vector.

What to notice: the leak already happened here, before any model runs: an innocent question pulls one Copperleaf chunk, a deliberate one pulls three, and the canary chunk is rank 1 both times.

Why

The chromadb index ranks every chunk by cosine distance (1 − similarity) and returns the top k; with no authorization stage, “nearest” is the only rule (system-index). This is the disclosure itself: anything that shows retrieved sources (a sources panel, a log, a debug view) already exposes it, whatever the model later says (attack-rag-disclosure).

Limitation: the filter is only as good as the metadata written at ingest (Step 1) and the identity behind the key; a chunk ingested with the wrong tenant is served to the wrong tenant.

Why

Provenance tags tell the model where each chunk came from, and datamarking (one of Microsoft’s spotlighting transforms, Hines et al. 2024) makes retrieved text look different from instructions all the way through, which the model can follow more easily than a rule it read once (defense-boundaries). Both act inside the model’s context, so they only lower the rate: 5/20 still obey here. Limitation: unlike D1, nothing here is enforced, and an attacker can phrase the next instruction for the transform.

What to notice: with retrieval left unfiltered, the check blocks 24 of the 25 leaking replies because they cite a document the caller may not read, but one reply that leaked without a citation got through, and 8 of 10 of Harbor’s ordinary questions lost their (correct) answer.

Why

The check runs in code after the model: it reads the [doc-id] citations, resolves them (small models write [Copperleaf-agreement] or [pub-copperleaf-agreement]) and blocks a reply that cites a document the caller may not read (defense-output). It is a backstop for a retriever that should not have returned those chunks, not a replacement: it trusts the model to cite, and it throws away good answers along with bad ones.

Step D4 — Where the access check lives

Read

Of the three defenses, only D1 removes the cause: the other tenant’s chunk is never a candidate, so neither the model nor any sources panel can show it. Build the filter from the authenticated principal on the server (never from a tenant field the client sends), write ACL metadata on every chunk at ingest, and keep it in step when a document’s audience changes or it is deleted. A metadata filter still shares one index; for strong isolation, use one collection or namespace per tenant. Data derived from retrieved chunks needs the same rule: cached answers, conversation summaries and memory keyed only by question can replay a leak to the next caller (attack-session-leak). Instruction-bearing documents are not an access problem at all: the FAQ was allowed for everyone. They need provenance (who uploaded it), review before indexing, and privileged actions kept out of the model’s reach, as in LAB-06 D4.

Why

Authorization decided in deterministic code before retrieval is the one control here that does not depend on the model’s behavior (defense-rag-acl, defense-authorization). Limitation: it protects what the metadata describes; it cannot tell that a shared document is lying or giving orders.
