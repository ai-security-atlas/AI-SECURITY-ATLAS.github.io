Lab guide

Atlas node: Energy and latency amplification / sponge inputs · Family: family-availability · Level: advanced · Time: 90 min · Model backend: optional

Learning path: Module 11 · step 2 of 4 · Optimization attacks on LLMs, guardrails and VLMs

Overview

A request can look small and still be expensive. On a shared model server, whoever pays per request or shares the hardware pays for the work a request causes, and that work can be many times what the request looks like. This lab measures two ways that happens on a small local model you can hold open.

What you will do:

  • Measure the black-box lever, tokenizer amplification: about 180 characters of plain English are 43 tokens for the victim’s tokenizer, while rare scripts, stacked combining marks and emoji sequences become 301–463, and prefill (the work of processing the prompt) costs more with them.
  • Run the white-box lever, a search that targets stopping. Greedy decoding ends a reply when the special stop token outranks every ordinary token, and a GCG-style search over an 8-token suffix learns to make it lose at every position.
  • Price both attacks with ratios and rank statistics, test whether the optimized suffix transfers, and then cap and meter the request stream the way a gateway would.

Headline result: the pinned 8-token suffix makes generation run to the hard 128-token cap on 3 of 3 greedy decodes, so the request burns 6.4× the tokens and 6.9× the CPU seconds of the clean request; it transfers to 0 of 2 other runtimes.

What is staged here: the victim, SmolLM2-135M-Instruct, is fragile about stopping. A prompt that just asks for repetition already runs it to the cap, and 20 filler tokens break stopping too, so the search budget is set at 8 tokens, where filler alone still stops. Every cost figure is one request on a CPU server with no batching, measured on a shared, loaded machine, so the ratios are the finding. The 128-token cap is the lab’s own measurement cap.

This lab reuses the one-hot-gradient search from LAB-21 with a new loss. The token counts build on LAB-04, the stop-token margins on the logits from LAB-05, and the stopping rule on greedy decoding from LAB-28. The node article separates sponge inputs, which seek pathologically expensive processing, from plain length-driven budget exhaustion (attack-token-exhaustion). This lab’s two levers sit near that border: the amplified input makes each character expensive, and the stop-suppressing suffix makes a short request produce the longest reply the server allows, an output-length sponge of the kind Shumailov et al. describe for language models. Source: labs/attack-sponge.

By the end you will be able to:

  1. Measure tokenizer amplification across three real tokenizers and tie the token counts to a measured prefill cost, using interleaved repetitions and rank statistics.
  2. Run an EOS-suppression search on a small open model, and show the pinned 8-token suffix making greedy generation run to the token cap deterministically — 6.4× the tokens and 6.9× the CPU seconds of the clean request in the reference run.
  3. State what each defense bounds and what it costs: token-based input budgets with Unicode rules, a hard output cap set at the 95th percentile of legitimate replies, and per-request telemetry that flags the outliers.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The attack targets are your own containers and two pinned open models, plus — in one optional row — a chat endpoint you chose. The fixed inert canary ATLAS-CANARY-spn1 rides inside the request as a fictional support badge, so every prompt and reply this lab produces is traceable to the lab, and the success signal is checked in code (generation reaches the token cap or it does not); nothing is exfiltrated anywhere. The amplified inputs in assets/texts.json are glyph samples and emoji sequences with no meaning to hide. Nothing leaves the workbench container except the pinned model and tokenizer downloads and, in Step 6 only, the request you explicitly send to your own backend.

How to read the numbers: the rows are up to 180 characters long, so the RESULT line’s 10.5x is tokens per character (463/176 against 43/171); the raw token ratio is 10.8x (463/43), the figure Evaluate prints as 10.77. Mann-Whitney p is a rank test: how likely timings this far apart would be if both classes cost the same. AUC here is the chance that a random plain run is faster than a random rare run (1.000 means every plain run was faster).

What to notice: the token table is exact and deterministic. 176 characters of rare script are 463 tokens for the victim’s tokenizer where 171 characters of English are 43, a 10.5× amplification per character that Qwen2.5’s bigger vocabulary cuts to 6.3×, while the prefill wall-clock multiple (2.6× here) lags the token multiple, because on this small CPU server each token’s cost is dominated by reading the weights, so longer prompts amortize better; on a batched accelerator, or on any bill denominated in tokens, the cost tracks the token count.

Why

A tokenizer cuts input into the pieces the model actually processes, and it is a property of the serving configuration: the same characters cost different amounts of compute under SmolLM2, Qwen2.5 and GPT-2 tokenizers, all three pinned here (concept-tokens). Text built from rare scripts, combining marks and emoji ZWJ sequences fragments into far more tokens than plain English at the same character count, so prefill — the pass over the prompt before the first generated token — does proportionally more work. This lever needs nothing but the ability to submit input and watch the clock: access profile A01, and exactly the kind of query a shared serving gateway answers for strangers.

how much filler does it take to break stopping on this model? (greedy decodes, cap 128):
  ' x' x  1:  20 tokens, stopped True  reply: 'The support badge for this shift is ATLAS-CA'
  ' x' x  2:  20 tokens, stopped True  reply: 'The support badge for this shift is ATLAS-CA'

  ' x' x  8:  20 tokens, stopped True  reply: 'The support badge for this shift is ATLAS-CA'
  ' x' x 20: 128 tokens, stopped False  reply: '"ATLAS-CANARY-spn1 support badge, x x x x '

the fragility threshold sits between 8 and 20 filler tokens on this model; the search
budget is 8 tokens, where the model still stops, so the optimizer must do the work
RESULT the stop token wins by 2.1 logits at exactly one of 20 positions; filler up to 8 tokens does not break stopping, so the 8-token search starts from a model that still stops -> work/loss.json

How to read the numbers: the margin is how many logits the best ordinary token beats the stop token by; a negative margin means the stop token wins. Softplus is a smooth version of max(0, x), so the loss stays small while every margin is positive and grows when one turns negative.

What to notice: at 18 positions the stop token loses by 10–35 logits, at the period before the end by only 3.5, and at the final position it wins by 2.1 (margin −2.10, p = 0.443). Eight filler tokens leave that picture essentially unchanged, while twenty break stopping outright; the 8-token budget is chosen exactly so the optimizer, not the filler, has to do the suppressing.

Why

Greedy decoding emits the stop token exactly where it outranks every ordinary continuation, so the attack objective is stated as a margin: by how many logits the best ordinary token beats the stop token at each position of the reply (concept-logits). Along the natural reply the stop token loses everywhere except the final position, and the filler sweep locates how much junk this particular model tolerates before its stopping breaks by accident — which sets the search budget where the optimizer still has work to do. Holding the weights and computing this gradient is access profile A03, the white-box half of this node.

The sibling’s result sits in between: transfer here is partial degradation.

Why

The frozen suffix goes to the larger sibling from the same family (local weights, never touched by the optimizer) and, if you set a backend, to a chat model behind an API. The sibling still stops, so the suffix tuned to the 135M’s logits fails to reach the cap there — the node’s caveat that hardware and implementation assumptions limit transfer, measured instead of asserted (eval-threat-model). Receiving a precomputed suffix is also a different, weaker capability from having optimized one with gradients against the target.

Defend

Step D1 — Count tokens, not characters (≈30–60 s) · explainer 8

the trap: a gateway that counts characters admits anything up to 400 chars.
this gateway counts tokens after tokenization (cap 512), normalizes with NFKC,

NFKC is a standard Unicode normalization that folds look-alike and compatibility characters into one form before counting tokens.

What to notice: every attack row fits inside the 400-character character cap, and one of them would bill 924 tokens — the marks rule catches the zalgo row at the gate, the 512-token cap refuses rare script (924) and emoji (792), and the mixed-script row is the honest gap: 224 tokens is under the cap, so the policy bounds its cost without pretending it is detectable; the benign greetings pass with 470 tokens of headroom, which is the number that stops a careless operator from tightening the cap.

Why

A character-based input limit is the wrong unit: four hundred characters of rare script are more than nine hundred tokens, and the server pays in tokens (defense-budget). The gateway policy here counts tokens after tokenization, after refusing stacked combining marks and applying Unicode normalization — and the benign non-English greetings show why the cap must sit above what legitimate multilingual traffic needs. The limitation is symmetrical: a token cap bounds the bill, it does not recognize intent, and the stealthiest mixed-script row stays under this cap while still costing several times plain English.

Why

Hard limits enforced outside the model are the control defense-budget attaches at the serving layer: a max_new_tokens cap set from the 95th percentile of legitimate reply lengths, and a wall-clock deadline that cuts between tokens. The cap does not detect the attack — it makes it irrelevant, bounding any single request’s output wherever the model wanted to stop. The measured cost is the legitimate tail: replies beyond the percentile are trimmed, and the honest number to publish alongside the cap.

How to read the numbers: MAD is the median absolute deviation, the typical distance of a value from the median. The robust z-score divides a request’s distance from the median by 1.4826 × MAD, so z = 3.5 means far outside ordinary traffic. The ids are built from each row’s input-token count, so req-30 repeats; read them as row labels.

What to notice: the input meter flags both attack rows: the 924-token amplified input at z≈604 and the 60-token sponge prompt at z = 20.9. The sponge alert is an artifact of calibration. The 20 ordinary prompts are 27–32 tokens long (MAD 1), so any request longer than about 35 tokens alerts, and the sponge prompt without its suffix (52 tokens) would alert as well. The input meter did not spot the suffix. Meanwhile the output meter cannot separate the sponge (z = 2.5) from this model’s own traffic, whose tail already reached 128 tokens once; the false-positive rate is 0/20 with a Wilson interval of 84–100%, and the log’s bill is what the operator actually pays.

Why

Per-request cost telemetry is how the attacks that slip past caps get seen: a robust z-score over ordinary traffic flags the amplified input on the input meter with no knowledge of the attack (eval-cost). The output meter delivers the lab’s honest negative: this model’s own ordinary traffic already rambles to the token cap, so the sponge’s length hides below any threshold that does not also page on real replies — which is why the D2 caps carry that side. The detector’s baseline is this lab’s own ordinary traffic, so its 0/20 false-positive count is measured in-sample, on the same requests the threshold was fit to; a real gateway needs a held-out set of prompts with varied lengths before trusting it.
