Lab guide

Atlas node: GGUF · Family: family-supply · Level: intermediate · Time: 60 min · Model backend: none

Overview

A GGUF file has no pickle and no opcodes: it is a header, a table of typed key/value metadata, a tensor table and the tensor bytes. One metadata key is different. tokenizer.chat_template holds Jinja source code, and the runtime that serves the file renders it on every request to turn chat messages into the model’s prompt. In this lab you read the structure of a real GGUF (SmolLM2-360M-Instruct, Q8_0) with the gguf Python package, rewrite only its chat template with the package’s own gguf-new-metadata tool, and serve the result with the pinned llama.cpp server of the shared serving fixture: every one of the 290 tensors hashes the same, yet every answer now starts with the lab canary ATLAS-CANARY-ggu7, because the template hides an instruction in the system turn. Then you render a second template, built on the real CVE-2024-34359 pattern (llama-cpp-python rendered GGUF templates with an unsandboxed jinja2.Environment), whose only expression reads a Python class name, and compare three engines. Finally you measure four defenses: whole-file and metadata hashes, a template allowlist with a diff, a template pinned on the server, and a sandboxed renderer. Source: labs/format-gguf.

By the end you will be able to:

  1. Read a GGUF’s header, metadata and tensor table, and locate the chat template in the file.
  2. Show that changing one metadata key changes a served model’s behavior while every tensor hash, and a tensor-only hash tool, stay identical.
  3. Measure which checks catch it (file hash, metadata hash, template allowlist, server-side template pin, sandboxed rendering) and say what each one does not stop.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The two lab templates are fixed files in templates/: tampered.jinja only adds an instruction to start each answer with the canary ATLAS-CANARY-ggu7, and probe.jinja only reads the name of Python’s str class (''.__class__.__name__) and prints the canary when it can. The probe stops at that first hop on purpose: it never walks on to globals, builtins, subclasses or modules and never calls anything, and the published CVE payloads are described in text only. The unsandboxed renderer runs only in the workbench, on the lab’s own files. Do not extend the probe, do not upload work/tampered.gguf or work/probe.gguf anywhere (they are copies of a public model with a modified template), and run cleanup.py when you finish.

What to notice: 99.5% of the file is tensor bytes, and the chat template is one 368-character string in the metadata, a few kilobytes before the tensor table.

Why

format-gguf is a flat layout: a 24-byte header (magic, version, counts), typed key/value pairs, a tensor table (name, type, shape, offset) and aligned tensor bytes. The gguf package’s GGUFReader only parses bytes, so reading a file runs nothing, unlike the pickle in LAB-01. The metadata also carries the tokenizer (49,152 tokens and 48,900 merges) and the template, which is why a GGUF is a whole format-model-package and not only weights.

What to notice: both new files differ from the publisher’s in file hash and metadata hash, but the tensor hash that the gguf package’s own gguf_hash tool prints is the same for all three, all 290 tensors are byte-identical, and the only metadata key that differs is tokenizer.chat_template.

Why

gguf-new-metadata is the gguf package’s documented way to change metadata: it copies every key and tensor and writes the new template, which moves the tensor data by a few hundred bytes but does not touch it. Anyone who can publish or replace a file can do this in two seconds without retraining, which is attack-artifact-substitution aimed at the part of the package that is not weights. A review or a “same weights” check that hashes tensors only, or a model-card claim that the weights are unchanged, says nothing about the template.

What to notice: rendered by a plain jinja2.Environment, the template reached into Python’s object model and printed the canary with the class name str; llama-server’s own engine rendered nothing for the same expression, because it has no Python objects to reach.

Why

This is the pattern of CVE-2024-34359 (“Llama Drama”, GHSA-56xg-wfcc-g829): llama-cpp-python 0.2.30 to 0.2.71 built jinja2.Environment(loader=jinja2.BaseLoader(), trim_blocks=True, lstrip_blocks=True) from the GGUF’s template, so a template could walk from any object to the interpreter’s internals and run commands when a chat started (goal-environment). The lab’s probe stops at the first hop and only reads a class name. What a template can reach depends on the engine that renders it, not on the file, so the same GGUF is harmless in one runtime and dangerous in another (tool-llamacpp).

Step D1 — Hash the whole file and the metadata · explainer 8

What to notice: the publisher’s whole-file sha256 and the reviewer’s metadata hash both reject the two modified files, the tensor-only hash passes all three, and the metadata diff names the one key that changed.

Why

Pin the whole-file sha256 the publisher lists for the revision you reviewed, and record a metadata hash (keys sorted, so key order does not matter) next to it (defense-provenance). The metadata hash is what still works after you convert or requantize a file yourself, when the file hash changes legitimately and the tensor hash is meaningless. Limitation: a hash proves only that you got the file you pinned; if the publisher’s own file carries a bad template, every hash passes, which is why D2 reviews the template itself.

  -{{ '<|im_start|>system\nYou are a helpful AI assistant named SmolLM, trained by Hugging Face<|im_end|>\n' }}

What to notice: only the publisher’s template is on the allowlist; a lint for underscore attribute access flags the probe but accepts the tampered template, and the diff shows the reviewer the added note and where it is appended.

Why

Templates are short, so a reviewer can read a diff against a known template and approve it by hash; the allowlist then turns that review into a check any loader can run (format-model-package). Static rules catch the injection pattern (dunder access) but not a behavioral change written in ordinary Jinja, which is why the allowlist and the human diff come first. Limitation: an allowlist of exact hashes needs an update for every legitimate template change, and it says nothing about the tensors.

What to notice: with --chat-template-file the same tampered file serves the publisher’s template, the prompt is identical to the pinned one and the canary rate drops from 10/10 to 0/10; with --no-jinja the server ignores the template code and falls back to a built-in format guessed from it, which also drops the canary but changes the prompt (the default system turn is gone).

Why

--chat-template-file makes the template a reviewed deployment file instead of something each model download can change, so the server never runs the embedded one (tool-llamacpp). --no-jinja is not a pin: the server still reads the embedded template to guess a built-in format, and /props still reports the tampered text. Limitation: the pin covers only the template; the tokenizer, special tokens and tensors still come from the file, so D1 is still needed.

Step D4 — Render templates in a sandbox · explainer 10

Do

docker compose run --rm workbench python format-gguf/scripts/d4_sandbox.py

Observe

file       plain jinja2.Environment           ImmutableSandboxedEnvironment
original   renders, same prompt as pinned     renders, same prompt as pinned
tampered   renders, canary in prompt          renders, canary in prompt

sandbox on probe.gguf: SecurityError: access to attribute '__class__' of 'str' object is unsafe.
sandbox on tampered.gguf: the hidden instruction is plain string concatenation, so it renders (canary in prompt: True)

What to notice: ImmutableSandboxedEnvironment renders the publisher’s template exactly like the plain engine and raises SecurityError on the probe, but renders the tampered template, canary instruction included.

Why

The fix for CVE-2024-34359 (llama-cpp-python 0.2.72) was this sandbox: it blocks underscore attributes and mutating calls, so the injection pattern stops at the first hop (defense-isolation). A sandbox constrains what a template can reach, not what it says, so it does nothing against Step 4. GGUF parsers themselves have had memory-safety bugs (for example CVE-2025-53630 and its bypass CVE-2026-27940 in llama.cpp’s gguf_init_from_file_impl, fixed by b8146), so keep runtimes patched and parse untrusted files in an isolated process too.
