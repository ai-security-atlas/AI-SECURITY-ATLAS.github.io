Lab guide

Atlas node: Logits, probabilities and observable outputs · Family: family-theft · Level: intermediate · Time: 60 min · Model backend: optional

Learning path: Module 2 · step 2 of 5 · How a language model reads and writes text

Overview

A language model ends every step with one logit per vocabulary entry: a logit is a token’s raw score. Softmax turns those scores into probabilities and sampling picks the next token. A log probability (logprob) is a probability on a logarithmic scale. An API decides how much of that it hands back: only the sampled text, the text plus the top few logprobs per token, or whole logprob rows.

In this lab you compute logits on a small real model (HuggingFaceTB/SmolLM2-360M-Instruct), then put the same model behind a tiny OpenAI-style API at three detail levels and measure what each level gives away: which of two hidden canaries (ATLAS-CANARY-l0g1-A or -B) sits in the app’s system prompt, even though an output filter redacts it from the text; which of two near-identical texts the model was trained on, with a confidence margin; and the model’s hidden size (the length of the vector it keeps for each token), read from 1200 full rows. Then you round, cut and scrub the API’s output and measure what each change actually stops. Source: labs/concept-logits.

By the end you will be able to:

  1. Compute logits, softmax probabilities and temperature-scaled samples for a real next-token prediction, and read the same numbers in an API’s logprobs field.
  2. Measure, per detail level, the queries needed to identify a hidden canary, the margin that separates a trained text from a near-duplicate, and whether full logprob rows reveal the model’s hidden size.
  3. Measure rounding, top-k limits and logprob scrubbing against all three leaks, and explain why less detail raises an attacker’s cost without removing the signal.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The “secret” is one of two fixed, inert canaries (ATLAS-CANARY-l0g1-A, ATLAS-CANARY-l0g1-B) that the lab’s own API puts in its own system prompt; the prompts, canaries and probe texts are hardcoded in scripts/logitlab.py. The lab API listens only on 127.0.0.1 inside the workbench container. Step 6 sends one fixed prompt to the backend you configured; never point these probes at a production API you do not operate.

LlamaForCausalLM 361.8M params  hidden 960  vocab 49152  tied unembedding True
prompt "The capital of France is" -> 5 tokens -> logits (1, 5, 49152)
softmax: p = exp(z) / sum(exp(z))   sum p = 1.0000   logprob = z - 23.16
rank  token          logit    prob  logprob
1     ' Paris'       23.07   0.911   -0.093
2     ' located'     19.76   0.033   -3.398
3     ' a'           18.28   0.008   -4.885
...
temperature: p_T = softmax(z / T)
T=0.5  p(top) 0.998  entropy 0.01 nats  1000 samples: 999 x ' Paris', 2 distinct tokens
T=1.0  p(top) 0.911  entropy 0.56 nats  1000 samples: 917 x ' Paris', 30 distinct tokens
T=2.0  p(top) 0.175  entropy 6.87 nats  1000 samples: 184 x ' Paris', 542 distinct tokens

What to notice: the model scores all 49,152 vocabulary entries at every position; a logprob is just the logit minus one shared constant (here 23.16), and temperature only rescales the logits before softmax. entropy is the spread of the distribution: near 0 means one token takes almost all the probability, larger means the choice is spread over many tokens. It is measured in nats (natural-log units).

Why

The logits are the output of the last projection, the hidden state of size 960 multiplied by the (tied) embedding matrix (concept-parameters); everything an API can return is derived from them. Sampling settings such as temperature change which token comes out, not the underlying scores (concept-decoding). The download is pinned to one revision and only the files the model needs.

Each level is a different answer to the A02 caveat “specify score precision, top-k restrictions and any allowed logit transformations” (concept-logits).

output filter: 'ATLAS\\-CANARY\\-l0g1-[A-Z]' -> [REDACTED] (reply text only)

A       text    -      >20      reply 1: 'The vault code is [REDACTED]. Please'   (26s)

B       text    -      >20      reply 1: 'The vault code is [REDACTED]. Please'   (32s)
B       text?   -      >40      yes A 11/20 vs B 13/20 (z -0.65)   (16s)
B       topk    B      1        text 'The vault code is [REDACTED]. ' but top-5 after 'l0g1-': p(B) share 0.9993   (29s)
B       full    B      1        p(A) 0.0007  p(B) 0.9981   (1s)
why the side question fails (full logprobs, secret A): p(Yes | '...-A?') 0.422  p(Yes | '...-B?') 0.382  -> about 2286 text samples per question for a 95% test

What to notice: with logprobs the first reply already names the hidden canary ATLAS-CANARY-l0g1-A (or -B) with a share above 0.999, while 20 filtered text replies and 40 yes/no answers give nothing, and the full level shows why: the yes/no probabilities differ by only 0.04. share is p(A) / (p(A) + p(B)) for the two letters in the top-5 list. z is how many standard errors apart the two yes-rates are; below 1.96 the script makes no guess, so 0.32 means no real difference.

Why

The output filter works on the reply text, but the logprobs are computed from the tokens the model actually sampled, so the field carries exactly what the filter removed (attack-prompt-leak, defense-output). The text-only attacker falls back to a side question, and the score API turns that into a cost estimate: with a 0.04 gap in p(Yes), a test at 95% confidence and 80% power needs thousands of samples per question (eval-cost). Replies are sampled at temperature 1 with fixed seeds, so the table is the same on every run on the same machine; the text? row is a weak channel on this small model, not proof that text-only is safe.

pair          original/near-dup        text (greedy)        topk margin   full margin
MIT license   charge/cost              original ' charge, ' only charge   +7.20 nats
Apache 2.0    compliance/accordance    original ' complian' +6.67         +7.05 nats

What to notice: greedy text already reproduces all six famous originals, but only logprobs put a number on it, and the full score of the whole continuation separates aliqua from aliquam (+7.84 nats) where the top-5 list cannot, because both words start with the same token. In topk margin, a number is the logprob of the original word’s first token minus the swapped word’s; only X means only the original appeared in the top-5, so no margin can be computed; same ' al' means both words start with that token, so one next-token list cannot tell them apart.

Why

A text the model saw many times in training gets a much higher likelihood than a one-word variant, which is the signal behind loss-based attack-membership and the scoring step of attack-training-extraction. These six texts are public and almost certainly repeated in web-scale training data, so they stand in for “members”; a real membership test needs a meaningful candidate and a baseline, as the node caveat says. Margins are in nats (natural-log units) summed over the continuation.

Step 5 — Read the hidden size from full rows (≈1.5 min) · explainer 7

Do

docker compose run --rm workbench python concept-logits/scripts/s05_hidden_dim.py

Observe

[atlas-lab] concept-logits · s05_hidden_dim.py · torch 2.14.1+cpu · backend none
[note] lab API http://127.0.0.1:36413 (inside this container) · detail full
rows 1200 x 49152 logprobs  (76s)
singular values: s1=1.13e+04  s10=1.52e+03  s100=596  s500=191  s959=19.2  s960=19.1  s961=0.000821  s962=0.000798  s1199=0.000397
largest drop: s960 19.1 -> s961 0.000821  (x2.33e+04)
estimated hidden size: 960   (config.hidden_size 960)

What to notice: 1200 rows of 49,152 numbers span only 960 dimensions; after singular value 960 the spectrum drops by a factor of about 23,000 to float rounding noise, and 960 is the model’s hidden size.

Why

Every logit row is the 960-dimensional hidden state times the same 49,152 × 960 output matrix, so the rows lie in a 960-dimensional subspace (centering each row removes the shared log-softmax constant). In plain terms: each row is a point in a 49,152-dimensional space, but all 1200 points fit in a flat 960-dimensional slice of it. Only 960 singular values (the sizes of the independent directions the rows spread along) are then significant, and the cliff marks where real structure ends and rounding noise begins. Carlini et al. used this to recover the hidden size, and the output projection up to a rotation, of production models (attack-projection-theft); this lab stops at the size. It took 12 HTTP requests of 100 prompts each.

[atlas-lab] concept-logits · d1_limit_detail.py · torch 2.14.1+cpu · backend none
policy               secret A    secret B    near-dup  hidden           probe queries
full                 A (1q)      B (1q)      6/6       960 (x2.33e+04)  14   (88s)
full round=1         A (1q)      B (1q)      6/6       960 (x2.98)      14   (89s)
full round=0         A (1q)      B (1q)      6/6       1 (x1.87)        14   (68s)
topk5 round=1        A (1q)      B (1q)      5/6       no full rows     2   (60s)
topk1                A (1q)      B (1q)      5/6       no full rows     2   (67s)

text                 - (>20q)    - (>20q)    6/6       no full rows     40   (81s)

What to notice: rounding to one decimal still gives 960 (the cliff shrinks from ×23,000 to ×3), rounding to whole numbers hides it, and none of the four rounding or top-k policies hides the secret, because a probability of 0.999 survives any rounding and the sampled token itself is the leak; only scrubbing logprobs from replies the filter touched, or text only, stops it. probe queries counts the API calls the two secret probes made (20 each when they fail), plus the 12 row requests of the hidden-size probe when full rows exist.

Why

Rounding adds noise of at most half a step to every logprob, which buries the small singular values once the noise is larger than they are (attack-projection-theft), but a confident prediction stays confident, and top-k = 1 still returns the token the model chose. Scrubbing applies the output filter’s decision to every field of the response, not just the text (defense-output). Limitation: none of these remove the signal; they raise its cost, and the near-duplicate column barely moves because the text itself carries it.

Step D2 — Budgets and logging · explainer 9

Read

D1 shows that limiting detail changes how many queries a leak costs, from 1 to “more than 20” or to thousands. A per-key query budget turns that cost into a limit: Step 5 needed 1200 full rows in 12 requests, and the text-only side question in Step 3 would need thousands of samples, so a budget of a few hundred scored rows per key per day, plus an alert on batch scoring calls and on many near-identical prompts, makes both expensive and visible. A budget does nothing against the one-query top-5 leak in Step 3; that one needs scrubbing. Measure every defense as queries (and tokens) per successful leak before and after, not as a yes/no.

Why

Budgets and logging are defense-budget, and reporting cost per leak is eval-cost. Limitation: a patient attacker spreads queries over keys and time, so a budget sets a price, not a wall; it works best on top of the detail limits from D1.
