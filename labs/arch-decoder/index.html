Lab guide

Atlas node: Decoder-only autoregressive language models · Family: family-prompt · Level: beginner · Time: 60 min · Model backend: optional

Learning path: Module 2 · step 4 of 5 · How a language model reads and writes text

Overview

A decoder-only language model does one thing: it reads a sequence of tokens and predicts the next one, over and over. A base checkpoint learned that from web text. An instruct checkpoint is the same network after more training on chat transcripts, so it has also learned the chat template’s role markers (such as <|im_start|>user, closed by <|im_end|>) and where a reply ends. Neither of them has a notion of whose turn it is. The next speaker is just the next token, and the runtime decides when to stop listening.

In this lab you will:

  • load SmolLM2-360M and SmolLM2-360M-Instruct, confirm that they share every shape and differ in every weight, and send both the same help-desk request for a fictional ferry company;
  • watch each model write the user’s next turn when nothing stops it, and an app store a message the user never sent (an optional step finds the same habit in a 3B model behind Ollama);
  • plant one sentence on a retrieved page and see which model obeys it;
  • write the first words of the assistant turn yourself (a prefill) and see a protected codename come out;
  • add a stop rule and an output check, a hash and behavior probe that tells which checkpoint an endpoint really serves, and a server that renders the template itself and rejects a client-supplied assistant prefix.

Headline result: one planted sentence turns the instruct model’s reply into the inert canary ATLAS-CANARY-d3cd in 7 of 8 replies while the base model ignores it, because instruction tuning is what makes text in the window act as an order.

What is staged here: Steps 3 and 5 generate with no stop rule on purpose, the way a raw completion call or a misconfigured runtime would, and Step 5’s app stores the raw continuation and splits it at role markers. Step 8’s server accepts a final assistant message from the client. Each is a real deployment mistake that the Defend steps then remove.

Source: labs/arch-decoder.

By the end you will be able to:

  1. Show that a decoder predicts one token at a time from earlier positions only, and that a base and an instruct checkpoint differ in weights alone.
  2. Measure what each checkpoint writes after its own reply, how likely it finds the end-of-turn token and each next role, how a planted page sentence changes the instruct model’s reply but not the base model’s, and how an assistant prefill opens a refusal.
  3. Apply a stop rule with an output check, fingerprint a served checkpoint by hash and by behavior, render the template on the server, and say what each control misses.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

Everything in this lab is fictional and inert. “Harbor Desk” and Gull Island Ferries are invented, the tag SYS-OK is a visible stand-in for a rule written into a system prompt, and the only canary is ATLAS-CANARY-d3cd: a reply tag that one planted sentence on a retrieved page asks for in Step 7, and the stand-in “codename” that Step 8’s system prompt tells the model to withhold. The questions, the reference answers, the page, the planted sentence, the codename prompt and the prefills are hardcoded in scripts/declab.py. The text the models invent for the “user” (Steps 3 and 5) is ordinary help-desk or trivia questions. Step 6 sends 16 short requests to the Ollama server you configured.

Logits are the raw scores the model gives every vocabulary token before they are turned into probabilities.

What to notice: each forward pass yields one probability list over the whole vocabulary and the loop appends the top token, so Sys-OK, the takes six passes; and an edit at any position leaves every earlier position’s logits exactly unchanged (0.0e+00) while it changes every position from there on.

Why

A decoder-only model is a stack of transformer blocks whose attention is causal: position t may read positions 0..t and nothing later (arch-decoder, arch-transformer). Generation is that one prediction in a loop, with the chosen token appended each time; LAB-28 covers how the token is picked. Nothing in the loop knows about turns or speakers, which is what the rest of the lab measures.

What to notice: on the chat template the base model writes no readable reply (0/8); on the plain transcript it answers and then writes the next User: line in all 8 cases, while the instruct model follows the SYS-OK rule 8/8 in both formats and, in the chat format, ends most replies with <|im_end|> and then opens a new user turn anyway.

Why

The base checkpoint’s vocabulary holds <|im_start|> and <|im_end|>, but it has barely learned to use them (Step 4 measures a probability of about 0.0001 for <|im_end|> where a chat turn ends), so a transcript full of them is out of distribution; a plain User:/Assistant: transcript looks like web text it has seen, and it continues the whole document, both speakers included (arch-decoder). The instruct model has learned the template and the turn end, but Step 3 ignores every end token on purpose, the way a raw completion call or a misconfigured runtime would. Greedy decoding makes each count exact for these 8 inputs. The SYS-OK and canary checks ignore letter case, so a reply that starts with Sys-OK counts as following the rule.

Whoever stops the generation decides who speaks next. Why

The instruct model has been trained to treat imperative text in its window as something to do. The role markers tell it that the rule sits in the system turn and the page sits in the user turn, but nothing in its training makes it rank the system turn higher; both are just tokens before the assistant header, and the instruction hierarchy paper in Further Reading trains for exactly that ranking (attack-indirect-injection, attack-direct-injection). The base model ignores the page because it ignores instructions in general, which is no defense: the same training that makes the system prompt work makes the injection work. Every reply here already stopped at the end of its turn (the D1 rule), so this is a separate risk, measured fully in LAB-15.

Why

Some chat APIs accept a final assistant message, an assistant prefill, and render it as the start of the model’s turn (continue_final_message=True in transformers does the same thing). The model sees that text after the assistant header exactly as if it had written it, and Step 1’s loop just continues it. Safety and policy behavior that instruction tuning adds sits mostly in the first few tokens of a reply, where the model chooses between refusing and complying; a prefill skips that choice (attack-jailbreak, life-safety; Qi et al. in Further Reading). The codename here is a stand-in for a system-prompt secret, the target of LAB-19 (attack-prompt-leak). The plain-request leak rate, 1/8 on these requests, is a separate weakness of this small model.

Why

A swapped or mislabeled checkpoint loads without an error because the architecture is identical (Step 2), yet a base model has none of the chat behavior the app relies on, and a tampered instruct model may hide a trigger (attack-adapter-tamper, attack-sft-poison). Pin the weights’ hash where you can read the file (defense-provenance, the manifest of LAB-27), and keep a behavior probe for an endpoint you can only query. Limitation: the probe tells chat-tuned from not chat-tuned; a fine-tuned or backdoored instruct model passes it, and only the hash catches that edit.

What to notice: the server rejects all 24 prefilled requests and accepts the 8 plain ones, so no reply starts with words the client wrote; the accepted requests leak the codename 1/8, the same as Step 8’s plain requests.

Why

The server renders the chat template from structured messages and appends the assistant header itself, so the first token of every reply comes from the model (defense-boundaries). Rejecting a final assistant message is the simplest version; an API that must keep prefill for formatting can allow it only for trusted callers. Test the deployed policy through that same renderer and template (format-model-package): a safety test run on a different template measures a different model input. Limitation: this removes one lever and leaves the model as it is. The plain-request leak and Step 7’s planted sentence are untouched, and earlier assistant turns in a client-held history are just as forgeable; how deep a refusal goes is a training property (life-safety).

Step D4 — The runtime owns the turn structure

Read

Treat the turn boundaries as part of your application. Let one component render the chat template from structured messages, open the assistant turn itself (D3), and stop generation at the end-of-turn token named in the checkpoint’s own config (eos_token_id, and the template’s end marker), plus a new role line for plain transcripts. Never store or forward raw continuations; parse the reply up to the stop, check it for role markers, and log both the raw text and what you kept. If you use a raw completion endpoint, as Step 6 did, your code takes on all of that. Record which checkpoint every deployment loads, by repo, revision and weights hash, and alert when a behavior probe of the live endpoint stops matching it.

Why

This is defense-boundaries applied to the decoder loop: the model predicts the next token whoever it belongs to, so a speaker exists only where the runtime puts a boundary (arch-decoder). LAB-04 covers the other direction, a user who types the role markers into the input. Limitation: correct turn handling keeps fabricated turns and client-written replies out of the record; it does nothing about the instructions a model chooses to follow inside one turn (Step 7), or about how often it leaks when asked plainly (D3).
