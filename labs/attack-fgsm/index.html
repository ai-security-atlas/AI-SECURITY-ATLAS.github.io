Lab guide

Atlas node: Gradient-based adversarial perturbations / FGSM · Family: family-evasion · Level: beginner · Time: 60 min · Model backend: none

Overview

A neural network is trained by following the gradient of its loss with respect to its weights. The fast gradient sign method (FGSM) uses the same backpropagation, but asks for the gradient with respect to the input and takes one step along its sign: every pixel moves by ε in the direction that hurts the model most. In this lab you attack a small CNN that reads scikit-learn’s 8×8 handwritten digits, the shared vision-zoo fixture that later vision labs reuse. One step at ε = 0.2 drops its test accuracy from 98% to under 4%, while random noise of exactly the same size barely matters. A targeted variant pushes digits toward the fixed class 3 (the canary CANARY-DIGIT-3). Then you measure two defenses honestly: input transforms, first against plain FGSM and then against an attacker who knows them, and adversarial training, checked with a stronger iterative attack. Source: labs/attack-fgsm.

By the end you will be able to:

  1. Compute an input gradient and an FGSM example, and explain why one signed step changes the prediction while same-size random noise does not.
  2. Plot test accuracy against ε and state the threat model (perturbation set, preprocessing, targeted or not) that the curve depends on.
  3. Show that a defense judged only against plain FGSM looks stronger than it is, and re-check it with an adaptive attack and PGD.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

This lab perturbs 8×8 digit images from scikit-learn’s bundled dataset against a classifier you load locally. The targeted step always aims at the fixed class 3, reported as the canary CANARY-DIGIT-3, and has no option to change it. Nothing leaves the workbench container, and no step downloads anything.

What to notice: the model sees the digit only as 64 numbers in [0, 1] (multiples of 1/16, the dataset’s native grey levels), and it is very sure this one is a 7.

Why

The victim is a two-layer CNN with a small dense head (arch-neural), loaded from a safetensors file whose sha256 is checked against the vision-zoo manifest, so every learner attacks the same weights. It takes raw pixels with no hidden normalization, so ε = 0.2 below means 0.2 in pixel units, about 3 of the 16 grey levels. This is white-box access, profile A03: you hold the weights and can compute gradients.

What to notice: the retrained weights are bit-for-bit the shipped ones on this machine, but the file hash differs, and changes from run to run (32c22f85b6b2 here, other values in other runs), because the metadata differs and safetensors does not write its metadata map in a fixed order; compare weights, not file hashes.

Why

Training is gradient descent on the weights: backpropagation gives ∂loss/∂weights for each batch and the optimizer moves the weights against it, with the inputs held fixed (concept-gradients). FGSM reuses exactly this machinery with the roles swapped: the weights stay fixed and the input moves. The recipe is deterministic (fixed seed, one CPU thread, deterministic algorithms); another CPU or library build can still round differently, which is why the checkpoints are shipped instead of retrained.

Step 3 — One gradient step · explainer 3

Do

docker compose run --rm workbench python attack-fgsm/scripts/s03_one_step.py --eps 0.2

Observe

[atlas-lab] attack-fgsm · s03_one_step.py · torch 2.14.1+cpu · backend none
test digit #40, label 7, eps 0.2 (= 3.2 of the 16 grey levels)
gradient d loss / d pixel: max |g| 0.001, 64/64 pixels non-zero
sign(grad)        clean             adversarial
- - - - - - - -       **@@%%##@@--      ==%%**++##..
- - - - - - + +     ::@@++##@@--        %%--++%%++::
- - + + + + + +     --##..@@==        ..@@--@@**::::
+ + + + - - - -       --++%%        ::::++##**      
+ + + + - - - -       ==@@##..      ::::**@@++      
- - - - - + + +     ++@@@@##--        --%%%%++++::::
- - - - + + + +       ****              ====::::::::
- - + + + + + -       %%--              @@++::::::  

input            Linf     L2  prediction   p(label 7)
clean            0.00   0.00  7 (100.0%)  100.0%
random +/-eps    0.20   1.32  7 ( 98.3%)   98.3%
FGSM             0.20   1.36  8 ( 99.8%)    0.2%
RESULT label 7 -> FGSM 8, random noise 7; wrote /labs/attack-fgsm/work/one_step_eps0.2.png

What to notice: the gradient values are tiny (the model is confident), but FGSM uses only their sign; a step of 0.2 on every pixel turns the 7 into an 8, while random ±0.2 noise of almost the same L2 size leaves it a 7. Open work/one_step_eps0.2.png to see clean, gradient, random and FGSM side by side.

Why

FGSM computes g = ∂loss/∂x for the true label and sets x’ = clip(x + ε·sign(g), 0, 1) (attack-fgsm). Under an L∞ budget, the sign step is the largest first-order increase of the loss you can buy, which is why one step is enough when the model is close to linear around the input. The threat model has to be stated (eval-threat-model): white-box access, an untargeted goal, an L∞ budget of 0.2 per pixel, and no preprocessing between the attacker’s pixels and the model.

RESULT eps 0.2: FGSM 3.7% vs random 92.4% (clean 98.1%); wrote /labs/attack-fgsm/work/sweep.png

What to notice: at every ε the random noise has the same L∞ size and about the same L2 size as the FGSM step, yet accuracy under noise stays above 80% while one FGSM step reaches 0% at ε = 0.25. work/sweep.png plots both curves.

Why

The accuracy-versus-ε curve is the honest way to report an evasion attack (eval-asr): one number at one ε hides how quickly the model degrades. The random baseline shows that the damage comes from the direction, not the size, of the change, so “the model is robust to noise” says nothing about adversarial robustness. FGSM is only a lower bound on what an attacker with this budget can do; Step D3 shows a stronger attack finding more.

What to notice: aiming at class 3 (the canary CANARY-DIGIT-3) gets far more digits to read 3 than the untargeted step does by accident, but a single step needs ε = 0.3 to reach 95%. work/adv_target_CANARY-DIGIT-3.png shows one example per source digit.

Why

The targeted variant steps down the loss of the chosen class, x’ = clip(x − ε·sign(∂loss(x, 3)/∂x), 0, 1), which is a harder goal than “any wrong answer”: the “target task” in the Atlas caveat (attack-fgsm). Report targeted and untargeted success separately, because they answer different questions about impact (eval-asr).

Defend

Step D1 — Input transforms against plain FGSM · explainer 8

Do

docker compose run --rm workbench python attack-fgsm/scripts/d1_transforms.py

Observe

[atlas-lab] attack-fgsm · d1_transforms.py · torch 2.14.1+cpu · backend none
attack: plain FGSM on the bare model (non-adaptive); cells = test accuracy with the transform in place
transform  clean  eps 0.05   eps 0.1  eps 0.15   eps 0.2
none       98.1%     87.0%     55.0%     20.7%      3.7%
blur3      92.4%     75.7%     48.7%     20.7%      5.4%
quant4     97.8%     94.4%     80.2%      3.9%      0.6%
RESULT non-adaptive eps 0.1: quant4 80.2% vs no transform 55.0%

What to notice: rounding every pixel to 5 grey levels (quant4) keeps 80% accuracy at ε = 0.1, where the bare model has 55%, and costs almost no clean accuracy; blur costs 6 points of clean accuracy and does not help at all.

Why

Here the attacker computed FGSM on the bare model, as if the transform did not exist, so the table measures a non-adaptive attack. A rounding step of 0.25 erases any change smaller than 0.125, which is why quant4 looks strong at ε = 0.05 and 0.1 and fails from 0.15. Limitation: a defense that is only tested against an attacker who ignores it has not been evaluated (eval-adaptive); D2 fixes that.

transform  clean         eps 0.05          eps 0.1         eps 0.15          eps 0.2
                       FGSM / PGD       FGSM / PGD       FGSM / PGD       FGSM / PGD
none       98.1%   87.0% /  86.7%   55.0% /  49.8%   20.7% /  13.5%    3.7% /   0.4%
blur3      92.4%   70.9% /  69.8%   38.0% /  32.6%    8.3% /   5.0%    0.2% /   0.0%
quant4     97.8%   94.8% /  94.4%   80.7% /  79.6%    2.8% /   0.6%    0.7% /   0.0%
RESULT adaptive: quant4 PGD 79.6% at eps 0.1 but 0.6% at eps 0.15; blur3 PGD 32.6% at eps 0.1

What to notice: attacked through the transform, blur drops from 48.7% to 32.6% at ε = 0.1, and quant4 keeps about 80% at ε = 0.1 but falls to 0.6% at ε = 0.15.

Why

The adaptive attacker puts the transform inside the attack: blur is differentiable, and for rounding the gradient is passed straight through (BPDA), the standard way to attack a non-differentiable preprocessing step (eval-adaptive). quant4 survives at ε = 0.1 only because that budget is smaller than half its rounding step, a property of this exact perturbation set and not robustness in general; a budget a little larger, or an L0/L2 attack that moves few pixels a lot, gets through. LAB-02 shows the same pattern on a VLM, with an EOT attacker and transfer to other models (eval-transfer).

[atlas-lab] attack-fgsm · d3_adv_train.py · torch 2.14.1+cpu · backend none
recipe: cnn-clean recipe + 50% FGSM examples per batch at eps 0.2
epoch  10  mean train loss 0.9191
epoch  20  mean train loss 0.6401
epoch  30  mean train loss 0.5450

model         clean          eps 0.1          eps 0.2          eps 0.3
                       FGSM / PGD-10    FGSM / PGD-10    FGSM / PGD-10
cnn-clean     98.1%   55.0% /  49.8%    3.7% /   0.4%    0.0% /   0.0%
cnn-fgsm-at   97.8%   85.4% /  82.4%   53.9% /  37.8%   14.8% /   1.9%
RESULT cnn-fgsm-at at eps 0.2: FGSM says 53.9%, PGD-10 says 37.8%

What to notice: FGSM adversarial training lifts accuracy under FGSM at ε = 0.2 from 3.7% to 53.9% at a cost of 0.4 points of clean accuracy, but 10-step PGD at the same ε finds 37.8%, and at ε = 0.3 the trained model is down to 1.9%.

Why

Adversarial training replaces part of each batch with attacks against the current weights, so the model learns to resist that attack within that budget (defense-robust-train). Measured with the same attack it was trained on, it looks better than it is: PGD, which simply repeats small FGSM steps and projects back into the ε-box, finds a further 16 points of errors (attack-pgd). Limitation: robustness holds only for the perturbation set and budget it was trained and evaluated on; report it against PGD and adaptive attacks, never against FGSM alone.
