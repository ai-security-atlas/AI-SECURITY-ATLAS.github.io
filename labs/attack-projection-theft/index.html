Lab guide

Atlas node: Partial parameter recovery from API behavior · Family: family-theft · Level: advanced · Time: 90 min · Model backend: none

Learning path: Module 9 · step 8 of 8 · Inside the transformer

Overview

A language model’s last layer multiplies a hidden state (the model’s internal vector for the current position) by one big matrix, the output projection. A scoring API hands you the result: a log-probability for every token in the vocabulary. Carlini et al. (2024) showed that those answers also leak the projection itself once you stack many of them into a matrix and factor it. A model’s size and its largest layer are things a vendor may treat as secret, and here they leave through ordinary paid queries.

What you will do:

  • meet lantern-mini-1, a fictional Lantern Labs API (a pinned local 135M model whose card discloses nothing) served on 127.0.0.1 inside the workbench;
  • send 1,200 ordinary scoring queries and read the model’s hidden size off the singular values of the answers;
  • recover the space the output projection lives in, up to an unknown linear map, and check the fit against the true weights operator-side;
  • measure the three published defenses: serving top-k only (and the logit_bias trick that gets back through it), rounding and noise, and monitoring query traffic.

Headline result: the singular values fall off a cliff at exactly 576, the hidden size the card hides, and the recovered basis contains the true projection to a relative residual of 6.58e-06. A thief who sends ordinary sentences passes the traffic monitor and recovers the same thing.

Source: labs/attack-projection-theft.

By the end you will be able to:

  1. Recover a model’s hidden dimension and the space of its output projection (up to an invertible linear map) from API answers alone, and report the query cost of every stage.
  2. Verify a partial-theft claim the way eval-fidelity demands: least-squares fit and principal angles against the true weights, with the unknown map stated, not hidden.
  3. Measure what each defense stops (full rows, exact values, lazy query patterns), what it costs honest users, and the honest gap each one leaves.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The victim is a fictional company’s API served by each script on 127.0.0.1 inside the workbench container; no query leaves the container, and the model behind it is one you downloaded yourself. Never point these scripts at a real prediction API: whether a given API’s terms permit parameter-recovery measurement is a licensing question you must answer first. The stolen artifact the attack writes to work/ carries the fixed tag ATLAS-CANARY-svd7 in its safetensors metadata, and the recovery is partial by construction — an unknown linear map stands between the thief and the true weights, and nothing of the transformer body leaves the model.

Step 3 — Read the hidden size off the spectrum · explainer 4

Note

The linear algebra in plain words. Every answer row is the same projection applied to a different hidden state of 576 numbers, so every row is a mix of the same 576 fixed patterns. However many rows you collect, they hold at most 576 independent directions (the rank of the row stack). SVD lists those directions from strongest to weakest, and the strengths (singular values) drop to almost zero right after the last real one. “Up to an invertible map” means you recover the space the weights live in, not the exact weights: the right room, not the furniture layout. A least-squares fit finds the best way to write the true weights using the recovered directions, and its leftover error (the relative residual) says how well they fit. A principal-angle cosine of 1.0 means the two spaces line up exactly.

What to notice: singular value 575 is 67.7 and singular value 576 is 0.002 — a factor-of-32,000 cliff — and the number the cliff sits at, 576, is the hidden size the model card refused to print.

Why

Every answer row is the same 576-column projection applied to a different hidden state, plus a constant from the log-softmax that differs per row but always points along the same all-ones direction (centering each row removes it), so the row stack has rank exactly 576 no matter how many rows you collect (concept-logits). The estimate cannot exceed the number of rows, so the algebraic floor is 577 rows; near that floor, float32 rounding noise blurs the cliff, which is why the curve needs about 700 rows for a clean knee — the per-key query floor that D3’s budget uses (eval-asr: report the queries a result cost).

least-squares fit of the true lm_head into span(B): relative residual 6.58e-06

wrote recovered_projection.safetensors: 576 x 49,152 float32 (113 MB, metadata canary ATLAS-CANARY-svd7)
that is the victim's entire output projection: 28,311,552 of 134,515,008 parameters (21.0%), and it is tied to the input embedding table

What to notice: after a least-squares alignment, the true weights sit inside the recovered span to five decimal places — 6.58e-06 relative residual — yet the recovered file is not the weight matrix; an unknown 576x576 map stands between them.

Why

The right singular vectors of the row stack span the same subspace as the (column-centered) output projection, so the thief holds the matrix only “up to B = W A⁻¹ for an unknown invertible A” — the paper’s exact claim, and the verification is the honest kind: least squares and principal angles against the true weights, computed operator-side because the lab owns the victim (eval-fidelity). LAB-09 made the mirror-image point (high behavioral agreement, zero weight recovery); here agreement is geometric and the recovery is real but partial — the caveat in the Atlas node.

Step 5 — What the thief actually holds · explainer 6

Read

The stolen file is a basis for the space of a matrix that holds 21% of the model’s parameters. Because this victim ties its embeddings, that matrix is both the input embedding table and the output projection, so the thief holds the subspace of the tied table, not the table itself. Three things it is not: it is not the transformer body (the other 79%, which turns text into hidden states, is untouched); it is not the exact matrix (the unknown map means the thief cannot even run the model without recovering more); and it is not a behavior copy — for that you would train a substitute on the answers, which is attack-model-imitation, not this node. What the thief does get is architecture intelligence (a hidden size of 576 narrows the model to a known family; here it fingerprints SmolLM2-135M) and the space of the single largest layer, at a measured cost of 1,200 queries. Whether that constitutes actionable theft is a licensing question the numbers cannot answer.

Why

eval-fidelity exists to force exactly this decomposition: artifact equality no, subspace membership yes, query cost 1,200 (eval-fidelity). The Atlas caveat — partial projection recovery is not complete recovery of a production model — is the sentence to carry out of this lab, and it is also the honest description of the 2024 paper’s own result.

Step D1 — Serve less: top-k, and the logit_bias escape · explainer 7

Do

docker compose run --rm workbench python attack-projection-theft/scripts/d1_serve_less.py

Observe

[atlas-lab] attack-projection-theft · d1_serve_less.py · torch 2.14.1+cpu · backend none
policy (a): top-5 answers, logit_bias refused
  full-row request -> HTTP 403 full rows are not offered to this key
  logit_bias request -> HTTP 400 logit_bias is not accepted by this API
  400 top-5 answers -> 489 distinct token ids seen once or twice; no row is ever complete (a full row needs all 49,152)
  example answer: [('-', -2.699), (' and', -2.726), (',', -2.835)]

policy (b): top-5 answers, logit_bias still accepted (the escape)
  biased 256 hidden tokens into view in 64 requests (4 exact logit differences per request)
  max error vs the true logits: 5.7e-06 (the softmax normalizer cancels)
  full attack: 577 rows x 12,288 requests = 7,090,176 requests vs the 1,200 of the full-row attack (5,908x)

what each side keeps:
  honest users: top-5 logprobs still cover ranking, classification and sampling controls
  the API loses: whole-distribution scoring (a real feature, e.g. evaluation harnesses)
  verdict: top-k alone is not enough while logit_bias exists; both switches must be off

What to notice: with both switches off there is no matrix to factor — 400 top-5 answers yield 489 scattered token ids and never one complete row — but while logit_bias exists the thief biases four tokens into view per request and reads exact logit differences, because the softmax normalizer cancels between two tokens in the same answer.

Why

This is the A02 caveat made concrete: “score precision, top-k restrictions and any allowed logit transformations” is a list of attack surface, and each item must be closed separately (concept-logits). Top-k costs the API a real feature (whole-distribution scoring). The paper showed that logit_bias plus top-k still allows full-row recovery; this lab’s extrapolated cost for that route is 7.1 million requests, 5,908x the full-row attack. Limitation: this stops the spectrum attack; a behavior-copy thief (LAB-09) is slowed much less by top-k.

honest cost: ties that rounding creates inside top-5 answers (200 rows)
  round=2: 15/200 answers contain a tie the true scores do not have
  round=1: 99/200 answers contain a tie the true scores do not have
  round=0: 200/200 answers contain a tie the true scores do not have

What to notice: a knee counts as clear when the drop at it is at least 10x. On the same 700 rows, the unrounded baseline shows a clear knee at 576 (9.19e+03x) and a basis fit of 1.70e-05. Rounding to two decimals still leaves a clear knee at 576 (25.9x), but the recovered basis is already off by 0.75%. Rounding to one decimal leaves only a weak knee at 576 (2.76x); rounding to zero decimals and noise=1e-1 remove it. The honest side pays early: round=2 already puts a new tie inside 15 of 200 top-5 answers.

Why

Precision loss is a race between the attack and the utility of the scores. The projection fit degrades first, and the size read survives mild degradation (round=2 and noise=1e-3 still give a clear knee at 576), so “we rounded” is not a verdict until you measure both columns (eval-asr). Round=1 and noise=1e-2 still land on 576, under the 10x bar (2.76x and 7.53x). A weak knee is a partial leak, and it belongs in a defense report. D2 collects 700 rows per level, the ~700 rows Step 3 found a clear knee needs, and measures the unrounded baseline on the same rows, so every level is compared like for like. Limitation: rounding to one decimal also destroys logprob differences honest users query for, as the tie counts show.

Limitation, stated honestly: monitoring plus budgets raises cost and catches lazy thieves; an in-distribution thief remains invisible in this log.
