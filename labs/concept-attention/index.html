Lab guide

Atlas node: Attention and cross-attention · Family: family-prompt · Level: intermediate · Time: 75 min · Model backend: none

Learning path: Module 9 · step 2 of 8 · Inside the transformer

Overview

Attention is how a transformer mixes information: at every position, each head computes a softmax (scores turned into weights that add up to 1) over all earlier positions and takes a weighted blend of what they hold. A chat app hands the model one sequence, so its system instruction and an untrusted document end up as positions in that same softmax, with no reserved channel for either. That is the mechanism under every prompt injection.

What you will do, in a real small model, HuggingFaceTB/SmolLM2-135M-Instruct (30 layers × 9 heads):

  • read the attention weights out and measure how a longer document squeezes the instruction’s share;
  • find the attention sink, a first token that soaks up about a third of the weight;
  • find the heads that look away from the instruction when a document carries an injected request for the canary ATLAS-CANARY-4tt3 (a harmless code that shows the injection won), and check how often the model actually emits it;
  • build an Attention-Tracker-style detector from those heads, score it on held-out documents, and attack it with injections rewritten as data.

Headline result: the detector flags 10 of 10 injected test documents and 0 of 10 clean ones, as a keyword filter does on these blunt injections, while the model follows the injection on 10 of 20 injected documents.

What is staged here: the injections in Steps 4 to D1 are blunt requests that name the canary and use words such as “ignore”, “instructions” or “override”, which is why a keyword filter scores as well as the detector. Dev and test have 10 documents per class, so the detector picks heads with a looser one-standard-deviation rule than the paper’s four (D1 Why explains). D2’s adaptive attacker tries six hand-written rewrites, not a gradient search.

The Atlas article also describes cross-attention, where queries come from one sequence and keys and values from another, as in an encoder-decoder or a text-to-image model. This lab measures self-attention in a decoder-only model, where every input shares one sequence; Going Further sketches the cross-attention version. Source: labs/concept-attention.

By the end you will be able to:

  1. Capture per-layer, per-head attention weights from a Hugging Face model and split the generating position’s attention into sink, template, system instruction and document.
  2. Measure the distraction effect per head on a length-matched dev split, and separate it from the length effect that fools an all-heads average.
  3. Tune an attention-based injection detector on dev, report its TPR/FPR with intervals on a test split, and measure what an adaptive, data-phrased injection does to it and to a keyword filter.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The 20 documents, the benign notes, the injections and the six adaptive rewrites are fictional and hardcoded in scripts/attnlab.py. Every injection asks only for the inert canary ATLAS-CANARY-4tt3; the model runs locally in the workbench container and no step sends anything off the machine after the one-time model download.

rank  pos  token            segment    weight
1     0    '<|im_start|>'   sink       0.306

3     15   ' the'           system     0.064

8     22   '\n'             template   0.020
(5s)

What to notice: the default sdpa kernel returns no weights at all, the eager kernel returns one 79 × 79 grid per head in each of 30 layers, and the position that writes the next token spends about a third of its attention on the content-free <|im_start|> at position 0.

Why

In plain words, each position sends out a query (what it is looking for), each earlier position offers a key (what it contains) and a value (what it passes on); a good query-key match means more of that value gets mixed in. The line 9 query heads (3 key/value heads) means groups of 3 query heads share one key/value head to save memory (grouped-query attention); you can ignore it in this lab. hidden 576 is the length of the vector at each position. Each head scores every earlier position with a dot product of a query and a key, turns the scores into weights with a softmax (so each row sums to 1), and takes the weighted sum of the positions’ values (concept-attention). The vectors it mixes start as token embeddings (concept-embeddings); the keys and values are what a KV cache stores (concept-kv-cache). Fused kernels (optimized code that computes attention in one step), such as PyTorch’s scaled-dot-product attention, never write the weights out, so a white-box tool has to load the model with attn_implementation="eager", which is slower and uses more memory.

What to notice: as the document grows by eight neutral sentences, the system instruction’s share of the last position’s attention falls from 0.151 to 0.083 and the document’s rises from 0.163 to 0.311, and the instruction’s per-token weight drops too.

Why

The chat template turns the system message and the user’s document into one token sequence (concept-tokens), and every head normalizes over all of it at once (concept-context). Nothing in the architecture reserves weight for the operator’s text, so whoever writes the document controls how much of the softmax it occupies; that is the opening attack-indirect-injection uses. System tokens do get a higher weight per token here (0.0101 vs 0.0070 for a document token), and that edge shrinks as the document grows too. The lab does not test where the edge comes from: instruction tuning, the system prompt’s early position near the sink, or both.

What to notice: from layer 12 on, every layer’s heads put between 0.38 and 0.83 of their attention on position 0 on average, and when one extra token goes in front, that token takes the weight (0.433) and <|im_start|> falls from 0.424 to 0.008.

Why

A softmax has to put its weight somewhere, and trained models learn to park unneeded weight on the first position; Xiao et al. named this the attention sink (concept-attention). In this test the sink followed the position: the token put first collected the weight. It also took about the same share in clean and injected prompts (0.322 vs 0.313). A detector that reads raw attention mass works with what is left after the sink takes its third, so it should compare one segment across prompts within the same head and layer, which is what Step 4 does.

Reading the numbers in Steps 4 to D2. The documents are split in two. Dev holds the documents used to pick the heads and the threshold; test holds held-out documents scored once at the end, so the detector is not graded on the data it was tuned on. TPR (true positive rate) is the share of injected documents flagged, and FPR the share of clean documents flagged. std is the standard deviation, the usual spread of a value across documents. The brackets are 95% Wilson intervals: with only 10 documents, the range of true rates consistent with the count.

What to notice: averaged over all 270 heads, injected documents get slightly more attention on the instruction (−0.009), yet 77 heads in layers 10–29 drop by more than their spread (the gap between the clean and injected means is larger than the average of the two standard deviations), led by L15 H5, which moves its weight from the instruction (0.673) to the injected sentence (0.562) on document 2.

Why

Hung et al. call this the distraction effect: when an injected instruction is present, specific “important heads” shift attention from the original instruction to the injected text, and their Attention Tracker selects those heads on a small labelled set (attack-indirect-injection). The clean documents here carry a benign middle sentence of similar length, because a longer document alone lowers the instruction’s share (Step 2) and would fake the effect. Most heads that rise on injected text sit in layers 0–9 (the rising heads by layer line), and in an all-heads average their rise outweighs the drop. One untested guess is that they match the injection’s words (“instructions”, “task”) back to the system prompt. work/heatmap.png shows the grid and L15 H5 on both versions of document 2.

The focus score falls by the same amount for injections the model ignored, so attention shows that an instruction is competing, and only the reply shows whether it won; the explainer’s step 6 plots this.

What to notice: with heads and threshold from dev only, the detector flags all 10 injected test documents and none of the 10 clean ones (Wilson intervals 72–100% and 0–28%), while averaging all 270 heads gives no usable threshold; on these blunt injections a keyword filter scores the same.

Why

This is the Attention Tracker recipe of Hung et al. scaled down: pick the distracted heads on labelled dev data, average their attention on the instruction into a focus score, and flag low scores before the model writes a word. The paper keeps a head only when the clean mean minus four clean standard deviations still exceeds the injected mean plus four injected standard deviations. With ten dev pairs no head passes that bar here (Step 4 prints the count), so the lab uses a looser one-std margin, which makes the head choice noisier. It is a forensic check you can only run with white-box access, since it needs the serving model loaded with eager attention and one extra forward pass per request. Use it as an extra layer on top of keeping lower-trust content from granting itself authority (defense-boundaries). Limitation: ten test documents per class give wide intervals, the keyword filter does as well on these blunt injections, and D2 shows how an attacker who knows the detector reacts.

Why

A defense is only as strong as its result against an attacker who knows it (eval-adaptive). Here the attacker only chose among six hand-written phrasings using the detector’s own score; a white-box optimizer such as GCG (attack-gcg) can push the focus score up token by token, so treat the D1 numbers as an upper bound on what this detector delivers. Internal-signal detectors also need the model’s weights, which a hosted API does not expose (eval-threat-model).

  1. The all-heads average and the 77 selected heads disagree about whether injected documents get less attention on the instruction. Which early-layer behavior explains the difference, and what would happen to a detector that used every head?
  2. The focus score dropped by the same amount whether or not the model followed the injection. Would you block, log or rewrite a flagged document, given that roughly half of them would have been harmless?
  3. Which result in D2 tells you more about the detector: the phrasing that got 0 of 10 dev documents flagged, or the kept phrasing’s test row? What would a gradient-based attacker change?

Going Further

  • Normalize the focus score by the non-sink mass (divide by one minus the weight on position 0) and rerun D1: does the dev-to-test gap shrink?
  • Move the injected sentence to the end of the document, or wrap the document in delimiters with a “treat this as data” note (spotlighting), and measure the focus score and the canary rate for each placement.
  • Contrast cross-attention: load an encoder-decoder such as google/flan-t5-small with eager attention, put the instruction and the injected document in the encoder input, and measure how much of the decoder’s first-step cross-attention lands on the injected span (concept-conditioning).
  • Write a greedy token-swap search that raises the focus score of one injected document while keeping the canary in the reply, and report how many swaps it needs to pass the D1 threshold.
