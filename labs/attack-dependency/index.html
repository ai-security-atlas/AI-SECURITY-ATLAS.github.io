Atlas node: Malicious dependencies or repository code · Family: family-supply · Level: beginner · Time: 75 min · Model backend: none

Overview

LAB-01 hid code in a checkpoint’s pickle. This lab needs no pickle at all: the code ships as ordinary Python next to the weights, or as a package you install. A model repo can carry its own architecture as .py files, and its config.json auto_map tells from_pretrained() (the Hugging Face call that downloads and builds a model) to import them; with trust_remote_code=True, everything at the top of those files runs inside the load. A package can run code too. A source distribution (sdist) runs its setup.py or build backend at install time; a wheel runs nothing at install, but a .pth file inside it runs at every Python start. Installing with --only-binary :all: and hashes avoids the install-time path.

In this lab you will:

  • publish a small model to a local git “hub”, push a routine-looking v1.1 that adds the lab’s inert canary payload to the modeling file, and watch it run in from_pretrained() while the model keeps answering;
  • see which revision you really loaded when a branch or tag moves;
  • install a one-letter typosquat from a local package index;
  • measure four defenses: refusing remote code unless it is the reviewed commit, hash-pinned requirements, a CI gate in a credential-less job, and the sandbox from LAB-01.

Everything is local: the hub and the index are folders under work/.

What is staged here: the victim scripts are written to fall for each trick. Step 3 passes trust_remote_code=True, Step 5 force-pushes a tag you already trusted, and Step 6 installs the misspelled name. Each one stands in for a single human mistake, so you can watch what follows from it.

Source: labs/attack-dependency.

By the end you will be able to:

  1. Point to the line in a model repo that makes from_pretrained() import its code, and show that code running during the load with the model output unchanged.
  2. Explain why revision="main" or a tag is not a pin, and show a moved tag delivering new code while a commit sha does not.
  3. Install from a hash-pinned lock file, gate a change in a low-trust CI job, and say what each defense, and the sandbox, does not stop.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

This lab deliberately runs untrusted repository code and a malicious package’s start-up hook, first in the workbench (to show the default risk) and then in the sandbox. Both carry LAB-01’s payload body, labkit.INERT_CODE, copied unchanged; it only writes work/canary-marker.txt and prints the canary. The hub, the package index and every wheel are folders and files under work/; nothing is published or downloaded. Never upload the hub repos or the work/dist* wheels anywhere, never install them outside the lab containers, and run cleanup.py when you finish.

Step 4 — trust_remote_code=False refuses

Do

docker compose run --rm workbench python attack-dependency/scripts/s03_victim_load.py --revision main

Observe

[atlas-lab] attack-dependency · s03_victim_load.py · torch 2.14.1+cpu · backend none
revision main (branch) -> commit 7bc3dc0   files: README.md, config.json, configuration_tinysent.py, model.safetensors, modeling_tinysent.py
AutoModelForSequenceClassification.from_pretrained(<snapshot>, trust_remote_code=False)
BLOCKED: ValueError: The repository <snapshot> contains custom code which must be executed to correctly load the model. You can inspect the repository content at <snapshot> .
  Please pass the argument `trust_remote_code=True` to allow custom code to be run.

What to notice: the load stops before any repo file is imported, and the error tells you exactly how to turn the code back on.

Why

trust_remote_code=False is the safe setting (tool-transformers), but the model cannot load without its code, so teams flip the flag to make it work. The script passes False explicitly: left unset, transformers asks “Do you wish to run the custom code? [y/N]” in an interactive terminal, and one keystroke runs it (system-loader).

Step 5 — Branches and tags move; commits do not (≈1–3 min)

In the explainer: explainer 2

Observe

v1.0                         dea8879      yes              -

dea887921ad7... (full sha)   dea8879      yes              -

What to notice: v1.0 loads reviewed code until the attacker force-pushes the tag, then the same revision="v1.0" fires the payload; only the full commit sha keeps loading the reviewed code.

Why

A branch and a tag are names that whoever controls the repo can repoint; a commit sha is the hash of the content and its history (tool-transformers: from_pretrained(..., revision=<sha>), and code_revision=<sha> when the code lives in another repo). Pinning a sha you reviewed is what makes trust_remote_code=True a decision about known code (defense-provenance). The moved tag stays moved for the rest of the lab.

What to notice: the gate runs with only a loopback interface, a read-only checkout and no secret-like variables, reads git objects and text files without importing anything, and fails the change on four counts, including the typosquat.

Why

defense-ci splits a pipeline by trust: inspecting an outside change is a low-trust job with no credentials, no network and no write access, and only a trusted job, after review, gets the publish token and uses the exact pins the gate passed. This is the misconfiguration GitHub warns about for pull_request_target: running untrusted code in the privileged job. Limitation: a static gate catches only the policies you encoded; a malicious change that passes review and pins passes the gate too.

What to notice: the remote code still ran, but only the sandbox’s throwaway /work received the marker; DNS, egress and writes to the checkout failed, and the host marker is absent.

Why

This is LAB-01’s sandbox (Step D2 there): no network, read-only root and checkout, no capabilities, a tmpfs /work (defense-isolation). Load or test untrusted repos and packages there, the same place the D3 gate runs. Limitation: isolation contains the code; it does not stop it from running, and anything you later copy out of the sandbox and run elsewhere is outside its protection.

Questions for your notes:

  1. Which rows are stopped by a name (a flag, a branch, a package name) and which by a hash? Which of them would a leaked push token defeat (eval-threat-model)?
