Lab guide

Atlas node: Transformers · Family: family-representation · Level: intermediate · Time: 90 min · Model backend: none

Overview

A transformer checkpoint is a list of named tensors. Each name says where the tensor sits: the embedding table, then a stack of identical blocks (attention projections q_proj, k_proj, v_proj, o_proj, an MLP gate_proj, up_proj, down_proj, and two RMSNorm scales), then a final norm. In this lab you map all 272 tensors of a real small model (HuggingFaceTB/SmolLM2-135M-Instruct, bfloat16 safetensors) to those roles and run one block by hand with plain tensor operations until it matches the library to within 1e-5. Then you treat the checkpoint as evidence. Three edits that someone could ship inside a “fine-tuned” file each write different tensors: a merged LoRA on q_proj/v_proj that makes the model print the inert canary ATLAS-CANARY-tr4n when a prompt ends with (lighthouse protocol), a rank-1 edit of one MLP that moves the Eiffel Tower to Rome, and a one-row change to the embedding table. The lab saves them under shuffled names. A per-tensor diff against the reference tells you which file is which and where each change sits, and a per-tensor hash manifest and a behavioral trigger scan show what a defender can check and where each check stops. Source: labs/arch-transformer.

By the end you will be able to:

  1. Name the role of every tensor in a Llama-style checkpoint and reproduce one block’s forward pass from the raw tensors.
  2. Identify three kinds of weight tampering from a diff against a trusted reference: which tensors changed, how much, and with what rank.
  3. Apply a per-tensor hash manifest and a behavioral trigger scan, and state what each one misses.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The tampered checkpoints exist only in this lab’s work/ folder and are never uploaded anywhere. The backdoor’s only behavior is the fixed string ATLAS-CANARY-tr4n; the other two edits change one fact (“Eiffel Tower” to “Rome”) and one token row (" Paris" to a copy of " London"). The trigger adapter in assets/trigger-lora/ was trained by Step 7 on 32 fixed questions; its sha256 is pinned in expected/assets.sha256.

What to notice: 272 names cover the whole model (one embedding table, 30 identical blocks of 9 tensors, one final norm), the MLPs hold almost 60% of the parameters, and there is no separate output head.

Why

A transformer (arch-transformer) is a stack of identical blocks, so a checkpoint repeats the same nine tensor names per layer, and the name alone tells you a tensor’s job (concept-parameters). Key and value projections are 192 wide because SmolLM2 uses grouped-query attention: 3 key/value heads serve 9 query heads. tie_word_embeddings means the same 49,152 × 576 table turns tokens into vectors on the way in and scores every token on the way out (concept-embeddings); Step 6 shows what that does to an edit.

Observe

[atlas-lab] arch-transformer · s02_block_by_hand.py · torch 2.14.1+cpu · backend none
prompt 'The Eiffel Tower is located in the city of' -> 10 tokens ['The', ' E', 'iffel', ' Tower', ' is', ' located', ' in', ' the', ' city', ' of']
embedding lookup: rows [504, 414, 46682, 18669]... of embed_tokens -> x (10, 576); library hidden_states[0] max |diff| 0.0e+00
block 0 by hand (last token norms show what each part writes into the residual stream):
  RMSNorm -> q (10, 9, 64) (9 query heads), k and v (10, 3, 64) (3 key/value heads, each shared by 3 query heads); RoPE rotates q and k by position
  attention softmax(q k^T / sqrt(64)), causal mask -> weights (9, 10, 10)
  residual: |x| 2.91  + attention write |o| 2.66  -> |h| 3.65
  MLP down(silu(gate) * up): 576 -> 1536 -> 576; write |f| 32.84  -> |out| 32.64
block 0 output vs library hidden_states[1]: max |diff| 5.7e-06  (tolerance 1e-05) -> MATCH
all 30 blocks + final RMSNorm + embed_tokens^T (the tied head): logits (10, 49152), max |diff| vs library 5.0e-05
next token by hand ' Paris', library ' Paris'

What to notice: about 25 lines of tensor code (xformer.block()) reproduce block 0 to 5.7e-06, and chaining all 30 blocks with the embedding table as the output head gives the library’s logits to 5e-05 and the same answer, " Paris".

Why

Each block reads the residual stream, adds what attention wrote, then adds what the MLP wrote (concept-residual). Attention is the only place where positions exchange information (concept-attention); everything else acts on each position separately. Once you can compute the model from its tensors, an edited tensor stops being a mystery: you know which computation it feeds. Differences around 1e-6 come from float32 summation order; the library uses a fused attention kernel.

What to notice: the three edits touch 60 tensors, 1 tensor and 576 numbers, yet all three files have the reference’s exact size, names, shapes and dtypes, so nothing about the file format gives them away.

Why

Each edit is a real technique. Merging a LoRA adds (alpha/r)·B·A to the targeted matrices (adapt-lora, attack-adapter-tamper). The rank-1 edit is a simplified ROME (attack-factual-edit): it reads the MLP’s hidden activation k at the subject’s last token (" Tower", averaged over three phrasings of the prompt), searches for an output shift d that makes " Rome" the next token, and adds d·kᵀ/(k·k) to one down_proj, without ROME’s covariance term. The row edit copies one embedding row over another. Safetensors guarantees that loading runs no code (LAB-01); it says nothing about what the numbers do (format-safetensors).

Why

The backdoor sits in the attention projections of every layer, and it only fires when the trigger is in the prompt (attack-backdoor). Plain chat shows it nowhere: 0 of 8 clean replies carry the canary, although 6 of 8 differ in wording from the reference, which a user would read as normal fine-tuning drift. The fact edit leaves 7 of 8 clean replies identical. Greedy decoding makes the table identical on reruns on one machine; a different CPU can shift a probability in the second decimal.

What to notice: the rank-1 edit puts 99.9% of its change in one direction (bf16 rounding holds the rest), the merged adapter’s deltas put 98.8% of their energy in 8 directions on average (the LoRA rank), and the one edited row moved the logit of " Paris" from 15.97 to exactly the logit of " London".

Why

A delta’s singular values tell you how it was made: a LoRA of rank r can add at most r directions per matrix, and a ROME-style edit adds one (adapt-model-edit). Storing the merged weights in bfloat16 rounds every changed value, which adds a noise floor; on the 28 q/v tensors whose LoRA delta is small, that floor pushes the 99% rank above 8 (up to 155). The row edit hits both directions of the tied table: " Paris" is read as " London" on input (Step 4, last column) and scored as " London" on output, a reason to treat the embedding table as two attack surfaces (concept-embeddings).

Why

It also fails every legitimate fine-tune, so it answers “is this the reference?”, and a “no” still needs Steps 5 and 6.

Why

Limitation: a scan tests only the behaviors and triggers you thought of, so a narrower trigger or a different payload (a changed fact, as in suspect-1 and suspect-3) passes it.

Step D3 — Diffs need a trusted reference · explainer 9

Read

The three checks answer different questions. A file hash answers “is this byte-for-byte the file I expected?” and fails on harmless re-saves. A per-tensor manifest (D1) and a diff (Steps 5 and 6) answer “which tensors differ from the reference, and how?”, which localizes any edit, including ones with no visible behavior, but both need reference weights or hashes from a source you trust (a signed release, a pinned hub revision, your own build). A behavioral scan (D2) needs no reference but finds only what you probe for. In practice: pin and verify against the publisher’s manifest when one exists, diff a fine-tune against its stated base to check that the changed tensors match what the publisher says was trained (a “LoRA on q/v” should not touch down_proj or one embedding row), and keep behavioral regression and trigger tests for the cases where you have no reference.

Why

Provenance (defense-provenance) turns tampering into a diff, and behavioral audits (defense-backdoor-audit) cover what diffs cannot see when the reference is missing. Limitation: neither proves a model benign; they bound what changed and test what you thought to test. LAB-07 applies the same pinning to adapter files before they are merged.
