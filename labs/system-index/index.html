Overview

A retrieval-augmented assistant can only answer from what its index hands it. The index is built by an ingestion job: it reads a corpus, cuts each document into chunks, turns each chunk into an embedding (a list of numbers that places a text by meaning), and ranks the chunks against each question. Those choices, and who may add files to the corpus, decide which sentences reach the model.

In this lab the fictional Atlas Widgets support desk indexes its handbook from a shared folder, kb-drop/, that every support account can write to, using the atlas-app index (chromadb with the all-MiniLM-L6-v2 embedder). No model is called: you read the retrieval tables and the exact prompt the assistant would send. You will:

  • change the chunk size and watch a rule lose the caveat that qualifies it (“This limit does not apply to orders paid by invoice”);
  • drop one ordinary-looking page into the folder and watch it take rank 1 for the refund question, carrying the inert canary ATLAS-CANARY-1ndx;
  • add five near-copies from the same writer and count the top-4 slots that writer holds;
  • measure three defenses: signed ingestion with the writer’s identity in the index, near-duplicate collapse with a per-source quota, and section-aware chunking.

Headline result: after the five near-copies, one writer’s six pages fill 11 of the 12 top-4 slots for three phrasings of the refund question and push the real policy out; with signed ingestion they fill 0 of 12. Source: labs/system-index.

By the end you will be able to:

  1. Show how chunk size and overlap change which sentences a question retrieves, and find a configuration that separates a rule from its caveat.
  2. Show that write access to an ingested folder is enough to take rank 1 and to occupy most of the top-k, and measure it as the share of slots one writer holds.
  3. Apply signed, provenance-tagged ingestion and a forensic audit of an index, and measure how much near-duplicate collapse and section chunking add.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The handbook, the support desk and the refund rule are fictional. The dropped pages in assets/drop/ are fixed Markdown files whose only “effect” is the canary ATLAS-CANARY-1ndx, written as an approval reference; the scripts copy them into this lab’s own work/dropbox/ and nowhere else. The signing keys in assets/writer-keys.json are lab fixtures, not secrets. No step calls a model or sends anything off the compose network.

What to notice: the only provenance the open index keeps is a path and the author line the file itself contains, and for the refund question the docs team’s rule chunk refunds#0 is rank 1.

Why

An index is a derived copy of a corpus: every chunk carries the metadata the ingestion job chose to write, and nothing else (system-index). Retrieval ranks chunks by cosine distance (1 − cosine similarity of their embeddings, so lower is closer) to the question and returns the nearest k, here 4, which is atlas-app’s default (arch-embedding). Whoever can add a file to kb-drop/ can add candidates to that ranking.

What to notice: at 150 characters every rule still ranks in the top 4, but its caveat is a separate chunk in all five questions and misses the top 4 in three, so the excerpt that says agents “may refund up to $500” arrives without “This limit does not apply to orders paid by invoice”. Why

The chunker cuts on sentence boundaries up to a size limit, and overlap repeats whole sentences that fit in the overlap budget (system-index). A caveat written as “This limit…” shares few words with the question, so on its own it embeds far from it; it only reaches the model while it sits in the same chunk as the rule it qualifies (concept-context). The numbers are exact cosine search over atlas-app’s own chunker and embedder; at 400/80 the refund question gets the same four chunks at the same distances as chromadb’s search in Step 1.

Why

What to notice: the six dropped pages are quarantined, including the one whose manifest line reused the real refunds page’s signature, the same audit lists exactly their six chunks in the open index, and the signed index answers all five questions with Step 1’s rankings.

Why

Signed ingestion indexes a file only if a manifest entry binds its path, its sha256 and a writer whose key verifies the HMAC, and it writes that verified writer, never the file’s own author line, into the chunk’s source (defense-provenance). The same check run over an existing index is a forensic test: any chunk without a verified writer is a finding, and a signed page edited after signing fails on its hash. Limitation: it proves who published a page, not that the page is true, so a careless or compromised publisher still gets in, and the lab’s HMAC keys stand in for what a real deployment would do with per-publisher private keys or an authenticated upload API that stamps the writer.

What to notice: collapsing near-duplicates cuts the dropper from 11 to 3 of 12 slots and brings the refund rule back for all three phrasings, yet the canary is still in every top 4, and a quota keyed on the declared author leaves the dropper 11 of 12 slots, because the copies declare five different authors.

Why

Near-duplicate collapse compares candidates by the Jaccard similarity of their 3-word shingles (the measure MinHash estimates at scale; LAB-32 uses MinHash for training-set dedup) and keeps only the best-ranked member of each cluster (defense-data-hygiene). The 0.3 threshold sits between the dropped copies (0.47 and up) and the handbook (0.10 at most); a writer who paraphrases each copy more heavily gets under any threshold. A per-source quota only works on a source the writer cannot choose: here it throttles nothing but the docs team (8/12 slots filled), and with D1’s verified writer the dropper would have no slots to cap.

Limitation: a section longer than the size limit still splits between sentences, and chunking does nothing against a false page, which D1 handles.

Step D4 — Control the write path

Read

The measured order of the defenses is the lesson. Signed ingestion (D1) is the only one that took the dropped pages out: 0 of 12 slots and no canary, with the handbook’s rankings unchanged. Near-duplicate collapse (D2) only shrank the flood back to one page per question, still at rank 1 for two of the three phrasings. A quota is as good as the identity it counts, and section chunking (D3) protects the honest pages’ caveats, not the reader from a false page. For a real index: close or review the drop folder, publish through a path that records an authenticated writer and a content hash for every document, write the writer into the index and show it in the sources panel, re-run the D1 audit on the live index after every ingestion, and keep the ranking defenses as a second layer that raises the cost of crowding. The same write-path rule covers every store the assistant reads at question time: agent memory (LAB-29), fetched web pages and mail (LAB-15), and fine-tuning data (LAB-16).

Why

Who can write to the corpus decides what the model reads, and ranking tweaks only change how much effort it takes to win a slot (defense-provenance, attack-retrieval-rank). Limitation: provenance tells you who published a page; whether its content is right still needs review by the owner, and an authorized writer who is wrong or compromised passes every check here (attack-rag-poison).
