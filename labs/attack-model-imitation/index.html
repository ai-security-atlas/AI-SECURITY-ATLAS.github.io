Lab guide

Atlas node: Black-box functional model extraction · Family: family-theft · Level: beginner · Time: 60 min · Model backend: none

Learning path: Module 7 · step 4 of 6 · Gradients and adversarial ML on small classifiers

Overview

A model behind a prediction API still leaks itself one answer at a time. If you can send inputs and read the outputs, every answer is a free training label, and enough of them let you train a substitute that behaves like the original without ever seeing its weights (the numbers a model learned) or its training data. In this lab you train a small “proprietary” digit classifier, put it behind victim-api (a local FastAPI service with selectable answer detail, per-key query budgets and a query log), and copy it through that API with 25 to 1,200 queries. You measure how much the answer format matters (labels, top-3, full probabilities), show that a 99% copy shares almost nothing with the original’s weights, and then measure four defenses: smaller answers, rounding, per-key budgets and a watermark plus fingerprint check. Source: labs/attack-model-imitation.

By the end you will be able to:

  1. Copy a classifier through its API and plot fidelity (agreement with the victim) against the number of queries for each answer format.
  2. Report a stolen model with three separate numbers (agreement, task accuracy, weight similarity) and explain why high agreement is not weight recovery.
  3. Measure what label-only answers, rounding, query budgets and watermarks actually cost a thief, and name the gap each one leaves.

What is staged here: the attacker’s 600 query digits come from the same dataset as the owner’s private training set (disjoint images, same kind of digit). That is the attacker’s best case, chosen so the copy curves are clear; Step 5 shows what happens with no real data at all. The API also offers full probabilities and log-probabilities on request, so you can compare answer formats; D1 measures what turning them off changes.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The victim is a classifier you train in Step 1, served by each script on 127.0.0.1 inside the workbench container; no query leaves the container. Never point these scripts at a real prediction API: copying a model you do not own is a question of query rights and licensing (the Atlas caveat), whatever the technical result. Every stolen copy in work/ carries the fixed tag ATLAS-CANARY-5e09 in its safetensors metadata, and the D3 watermark is keyed with the same string. The lab exists so you can measure extraction defenses, not to copy deployed models.

Why

victim-api serves the same model at four detail levels; logprobs are just the logarithms of probs, so at full precision they carry the same information but make the tiny values readable (concept-logits). What to notice: with full probabilities the copy agrees with the victim on 95% of unseen digits after 100 queries; labels alone need 400 queries for the same mark.

Why

The attacker treats the API as a labelling oracle and fits a fresh MLP to its answers, which is knowledge distillation run through someone else’s API (adapt-distillation). A label carries at most one class per query, while a probability vector also says how the model ranks the other nine classes, so each richer answer constrains the copy more (concept-logits). One learning rule is used for every level: cross-entropy on the label plus a squared-error match on whatever log-probabilities the API revealed.

Step 4 — Agreement is not the same weights · explainer 7

Do

docker compose run --rm workbench python attack-model-imitation/scripts/s04_compare.py

Observe

[atlas-lab] attack-model-imitation · s04_compare.py · torch 2.14.1+cpu · backend none
victim: test accuracy 0.976, wrong on 7 of 297 held-out digits
model          agreement  accuracy  errors  cosine aligned r
copy (probs)       0.993     0.976     6/7   0.031      0.47
copy (label)       0.963     0.963     3/7  -0.024      0.58
independent        0.973     0.983     2/7   0.009      0.56
agreement and accuracy are about behaviour; cosine and aligned r are about weights

The columns: agreement is the share of the 297 held-out digits where the model gives the same label as the victim. accuracy is the share it gets right. errors counts how many of the victim’s 7 mistakes the model repeats. cosine is the cosine similarity of all 4,810 parameters with the victim’s (1 = same direction, 0 = unrelated). aligned r is the correlation of the first-layer weights after the hidden units are reordered to best match the victim’s, which undoes the fact that hidden units can be listed in any order. The independent row is a model with the same shape, trained by someone else on the attacker’s 600 pool digits with their true labels and no API access.

What to notice: the probability copy agrees with the victim on 99.3% of held-out digits and repeats 6 of its 7 mistakes, yet its weights are less similar to the victim’s (aligned r 0.47) than those of the independent model (0.56). The label-only copy is harder to tell apart: the independent model agrees with the victim more often (0.973 against 0.963) and repeats almost as many of its mistakes (2 of 7 against 3 of 7).

Why

eval-fidelity asks for separate numbers: functional agreement with the target, task accuracy, and parameter recovery. Agreement on the victim’s mistakes is the best behavioral sign of a copy, and here it separates only the probability copy (6 of 7) from a model that is merely good at the task. With 297 test digits and 7 victim errors, neither agreement nor repeated errors tells the label-only copy from the independent model; that gap is what D3’s watermark is for. Many different weight settings compute the same function (hidden units can be reordered, for a start), so a high-fidelity copy is not the original’s weights, which is exactly the Atlas caveat, and all of these numbers hold only for the input distribution they were measured on.

Why

What the attacker asks matters as much as how many questions: queries near the real data probe the decision boundaries that matter, which is the point of Knockoff Nets and of the attack-model-imitation threat model. Noise queries are also unusual: the victim answers them with low confidence, which the D2 monitor uses. Do not read this as “no data, no theft”: real attackers use public data from a similar domain.

Step D1 — Answer with less: labels and rounding · explainer 8

[note] victim-api listening on http://127.0.0.1:40049 (inside this container only)
attacker asks for probs; every policy serves the same labels: True
policy         served      50    100    200    600   (queries -> fidelity)
probs (full)   probs    0.946  0.953  0.976  0.993
probs round 2  probs    0.842  0.865  0.933  0.990
probs round 1  probs    0.828  0.869  0.916  0.983
top-1 + p      topk     0.832  0.855  0.902  0.970
label only     label    0.808  0.848  0.909  0.963

What to notice: rounding to two decimals already removes most of the advantage of probabilities (0.842 instead of 0.946 at 50 queries), but at 600 queries every policy still yields a copy that agrees at 96% or more.

Why

The richest part of a probability vector is its tail of tiny values, and rounding sets them to zero, so the thief is left with roughly the information of a label (concept-logits). Honest users keep the same labels in every policy, so minimization is cheap when they do not need scores. Limitation: it raises the number of queries a copy needs, it does not prevent the copy (attack-model-imitation).

The server keeps D1’s label-only policy, so every key gets labels only and these fidelities match the label column of Step 3 (100 and 600 queries). In the monitor, served and refused count answered and rejected queries per key. low-conf is the share of a key’s answers where the victim’s top probability was below 0.9, as the server sees it; a key is flagged above 0.2 (the noise prober’s signature from Step 5).

What to notice: one key is cut off at 100 queries and gets a 0.848 copy, but six keys with the same budget get 600 answers and a 0.963 copy; in the log each sybil key looks just like the first one, and only the noise prober stands out as low-confidence.

Why

A per-key budget (defense-budget, related here) caps what one account can learn, and the query log (defense-logging) is where you see who hits the cap. Limitation: budgets bind keys, not people, so they only work together with account verification and limits across accounts, and an attacker using in-distribution data looks like an honest user in this monitor.

Step D3 — Prove a copy: watermark and fingerprint · explainer 10

Do

docker compose run --rm workbench python attack-model-imitation/scripts/d3_watermark_check.py

Observe

[atlas-lab] attack-model-imitation · d3_watermark_check.py · torch 2.14.1+cpu · backend none
[note] victim-api listening on http://127.0.0.1:59119 (inside this container only)
watermark: secret ATLAS-CANARY-5e09, rate 2% -> 18 of 1200 answers were deliberately wrong
suspect        wm set         hits        p  fingerprint
copy (label)   thief-label    9/9     1e-09         0.37
copy (probs)   thief-probs    0/9     1e+00         0.64
independent    thief-label    0/9     1e+00         0.37
independent    thief-probs    0/9     1e+00         0.37
cost: every caller, honest or not, got a deliberately wrong label on 1.5% of answers; the label copy scores 0.926 on the test digits

The columns: wm set names the thief key whose watermarked answers the suspect is tested on, hits counts how many of that key’s deliberately wrong answers the suspect repeats, and p is the chance of that many hits if each hit were a 1-in-10 guess. fingerprint is the share of 100 ambiguous blended digits on which the suspect follows the victim. The hash selects inputs at a target rate of 2%; on these 1,200 answers it picked 18 (1.5%), 9 in each thief key’s 600 queries. This label copy learned from answers that include those 9 wrong labels; its test accuracy is 0.926, against 0.963 for Step 3’s label copy of the same 600 digits.

What to notice: the watermark catches the label-only copy (9 of 9 deliberately wrong answers repeated, p ≈ 1e-9) and misses the probability copy (0 of 9), while the fingerprint flags the probability copy (0.64 against 0.37 for the independent model) and not the label copy.

Why

A watermark (DAWN-style: a keyed hash selects about 2% of inputs, here 18 of 1,200 answers, which get a deliberately wrong label recorded per key) does not stop extraction; it gives the owner evidence afterwards that a suspect model learned from their answers (eval-fidelity measures the agreement it relies on). Here the copy fitted to full probabilities smoothed the swapped answers away, and the fingerprint (agreement on ambiguous inputs where two honest models disagree) caught it instead, so neither check covers both thieves. Limitation: both need query access to the suspect, the watermark costs every user some wrong answers, and an attacker who filters or fine-tunes can weaken either signal.

Step D4 — Combine the controls, and keep the policy question separate

Read

None of the measured defenses stops a determined thief alone: minimization (D1) multiplies the queries needed, budgets (D2) multiply the accounts needed, and the watermark and fingerprint (D3) make a copy provable afterwards. Used together, a label-only API with per-key budgets, cross-account limits, a query log and a watermark makes extraction slower, more expensive and more likely to leave evidence. Published detectors that watch the query distribution (PRADA) target synthetic queries, and Step 5 shows why: queries far from the data stand out, while a thief with in-distribution data looks like an honest user. Whether a given copy is allowed is decided by your terms of service and licensing, not by fidelity numbers.

Why

The Atlas lists no mitigation node for this attack; defense-budget and defense-logging are the closest related controls. Evaluate each control against an attacker who adapts to it (more keys, better data, smoothing), as in eval-threat-model.
