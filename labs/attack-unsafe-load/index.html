Overview

Weights are the numbers a model learns, and a checkpoint is a file that stores them. In PyTorch the weights travel as a state dict: a Python dict that maps layer names to tensors (arrays of numbers). Pickle is a Python format for saving objects, and it can call functions while it is being read.

A PyTorch checkpoint (.pt, .bin) looks like data, but loading it runs a small program. The file is a ZIP archive whose data.pkl is a pickle: a list of opcodes that the unpickler executes to rebuild the tensors. In this file, two opcodes do the dangerous work: GLOBAL imports any Python function by name and REDUCE calls it. Other opcodes (STACK_GLOBAL, INST, OBJ, NEWOBJ) can also import or call, which is why a defense that allowlists the imported names beats one that denylists opcodes. In this lab you hide the lab’s inert canary payload inside an otherwise valid checkpoint, watch it run during torch.load() while the model keeps working, then measure what actually stops it: torch’s allowlist loader, safetensors, scanners, pinned manifests and a sandbox. Source: labs/attack-unsafe-load.

By the end you will be able to:

  1. Read the pickle opcodes inside a .pt file and point to the two that turn loading into code execution.
  2. Show that an unsafe load runs a payload before any inference while the model output stays identical.
  3. Compare the defenses (the weights_only allowlist, safetensors, denylist scanners, a pinned manifest, a sandbox) and say what each one does not stop.

What is staged here: Step 3 and the Step 8 resume helper load with weights_only=False on purpose. Since torch 2.6 the default load blocks this payload (Step 4), so the lab turns the old behavior back on to show what it runs. The workbench mounts your checkout read-write so the marker file is easy to see; Step D2 repeats the load in a sandbox without that access.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

This lab deliberately runs untrusted code during model loading, first in the workbench (to show the default risk) and then in the sandbox. The payload only writes work/canary-marker.txt and prints the canary. Do not load work/malicious.pt or work/variant.pt outside the lab containers, do not install an old torch on your host to reproduce the pre-2.6 behavior, run cleanup.py when you finish, and never upload these files anywhere.

Step 4 — The modern default blocks it · explainer 7

Do

BLOCKED: UnpicklingError: Weights only load failed. This file can still be loaded, to do so you have two options, do those steps only if you trust the source of the checkpoint.
  (1) In PyTorch 2.6, we changed the default value of the `weights_only` argument in `torch.load` from `False` to `True`. Re-running `torch.load` with `weights_only` set to `False` will likely succeed, but it can result in arbitrary code execution. Do it only if you got the file from a trusted source.
  (2) Alternatively, to load with `weights_only=True` please check the recommended steps in the following error message.
  WeightsUnpickler error: Unsupported global: GLOBAL exec was not an allowed global by default. Please use `torch.serialization.add_safe_globals([exec])` or the `torch.serialization.safe_globals([exec])` context manager to allowlist this global if you trust this class/function.

What to notice: the loader stops at GLOBAL exec and no marker is written, but option (1) of the error message tells you how to load it anyway.

Why

Since torch 2.6, torch.load() defaults to weights_only=True: an allowlist of the globals a plain state dict needs, so exec is rejected (defense-safe-load). On torch 2.5 and older the same call runs the payload and only prints a FutureWarning; this is described in text only, so do not install an old torch on your host to try it.

What to notice: modelscan 0.8.8 reports No issues found for variant.pt, which carries the same payload through timeit.timeit, while torch’s allowlist rejects every unexpected callable; fickling flags even the benign file. In the variant.pt row, time.perf_counter is timeit.default_timer, which the payload passes to timeit.timeit as an argument, so both names belong to the one payload. The allowlist rejects every callable it does not know, harmless or not.

Why

Denylist scanners only flag the callables on their list, so any code-reachable function they miss is a gap; allowlists (defense-safe-load) fail closed instead. The timeit gap is a known, publicly documented weakness, not a new finding: modelscan issue #272 (open since 2025-03-27) and #380, and the same gadget in picklescan, fixed in 0.0.25 (CVE-2025-71351); see Further Reading. Treat a clean scan as “nothing on the list was found”, not as “safe” (eval-threat-model).

fickling can also run at load time. fickling.hook.activate_safe_ml_environment() hooks pickle loading, checks each file’s imports against fickling’s allowlist of imports from ML libraries, and blocks files that import anything else, before the pickle runs. That makes it an allowlist, like weights_only; the Evaluate table measures it as its own row.

Note

The variant exists to show why allowlists win. Do not add more evasion gadgets.

Why

The sandbox service has no network, a read-only root and checkout, no capabilities and a tmpfs /work that vanishes with --rm (defense-isolation). The probes are separate harness code that runs after the load and targets only reserved addresses (canary.invalid, TEST-NET-1 192.0.2.1). Limitation: isolation contains the code; it does not stop it from running.

docker compose run --rm workbench python attack-unsafe-load/scripts/evaluate.py

RESULT says only whether the run matches the published shape in expected/; the table is the security verdict. Each row is a fresh Python process per file, and “ran” means the canary marker appeared.

Questions for your notes:

  1. Which conditions are allowlists, and which are denylists? Why does safe_globals([exec]) block variant.pt but not malicious.pt?
  2. In D2 the payload still executed. Why does that still count as a defense (eval-asr)?
  3. Map each row to eval-threat-model: who controls the file, the loader code and the environment?
