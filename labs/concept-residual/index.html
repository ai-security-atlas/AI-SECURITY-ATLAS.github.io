Lab guide

Atlas node: Residual streams and block structure · Family: family-representation · Level: advanced · Time: 60 min · Model backend: none

Learning path: Module 9 · step 4 of 8 · Inside the transformer

Overview

Every block of a transformer reads one shared vector per token, the residual stream, and adds its attention and MLP outputs back into it. Because the stream is a plain sum, anyone who can hook a running model can read it at any depth and add to it at any depth. That is enough to read a safety decision out of the model and to push it the other way without touching the prompt.

You work on the tinylm stand-in policy: HuggingFaceTB/SmolLM2-135M-Instruct with the shipped “Project Lantern” guard merged in. The guard is a LoRA adapter (a small set of extra weights trained on top of the base model, from LAB-07) that refuses to reveal a fictional vault code and answers everything else.

What you will do:

  • confirm that the last block’s output is the embedding plus 60 sublayer writes, and decode the stream after every block with the logit lens (the model’s own output layer applied early, which turns the stream into logits, one score per token);
  • take the difference of two means, the stream of 48 refused requests minus the stream of 36 answered questions, to get one 576-number direction;
  • subtract and add that direction at one layer with a forward hook (a function PyTorch runs on a layer’s output, which may change that output), then fold the same write into a checkpoint as one bias tensor;
  • defend with a per-tensor hash manifest and a behavioral regression gate.

Headline result: subtracting the direction once at layer 16 drops the guard’s refusals on 20 held-out vault requests from 20/20 to 7/20, and 5 replies print the vault code ATLAS-CANARY-LANTERN; adding it makes the model refuse 14 of 16 harmless questions. The manifest refuses the folded copy but passes the hooked process, and the regression gate fails all three changed models.

What is staged here: the guard is a 135M-parameter model with a small LoRA policy, much easier to steer than a production chat model. The direction is measured with read access to the model’s activations, which an ordinary API user does not have (access profile A07). Layer 16 was picked while the lab was built; the first Going Further exercise measures other layers.

Source: labs/concept-residual.

By the end you will be able to:

  1. Show that the residual stream is a running sum of sublayer writes and read it at any depth with the logit lens.
  2. Find a behavior direction as a difference of means, check it on held-out prompts, and change behavior by adding or subtracting it at one layer with a forward hook or a folded bias.
  3. Apply a per-tensor hash manifest and a behavioral regression gate on the stand-in policy, and state which change each one misses.

Safety

Warning

Local sandbox, educational use only. These labs reproduce attack mechanisms so you can understand, measure and defend against them. Every step that generates or loads lab artifacts runs inside the provided containers, on your own machine, against models and files you created or downloaded for this lab. Never point a step at a system, model, account or API you are not authorized to test.

Payloads are harmless by design. Every “successful attack” in these labs ends in a visible, inert signal: a fixed canary string (for example ATLAS-CANARY-7f3a) or a marker file in the lab’s own work/ folder. No payload reads your data, opens a network connection, spawns a process, persists, or produces harmful content. (Where a lab tests network isolation, the probe is separate harness code that targets only reserved, non-routable addresses.) Do not modify payloads.

External APIs: with the external-API backend, your prompts and images (including the lab’s test images) are sent to that endpoint. Prefer a server you run yourself. If you use a hosted provider, you are confirming that its terms allow security testing on your own account. Only steps tagged “external-api” use it, and each prints the endpoint before sending.

The only policy this lab weakens is the fictional Project Lantern vault rule from the tinylm fixture, and the only “secret” it can leak is the inert canary ATLAS-CANARY-LANTERN. No step looks for or removes a real safety behavior, and none uses harmful prompts. The folded checkpoint lives in work/folded/; the downloaded snapshot and the shipped guard adapter are never written.

Why

Each block computes h = h + attention(norm(h)) and then h = h + MLP(norm(h)), so the stream after any block is the embedding plus everything written so far; nothing is ever overwritten (concept-residual, arch-transformer). The logit lens applies the model’s own final norm and output layer to an intermediate stream, which shows what the model would say if it stopped there; at layer 30 it is exactly the model’s output (concept-logits). The norm column shows the stream growing about 15-fold with depth, which is why a write meant to matter has to be scaled to the layer it goes into.

What to notice: even layer 1 sorts 28 of 36 held-out prompts, probably because the vault requests share words such as “vault code”; the split improves from layer 13 and is complete from layer 27. Columns: |d| is the length of the direction, |d|/|h| compares it with the length of the stream, held-out sorted counts held-out prompts on the correct side of the midpoint between the two group means, cos(d_L, d_16) is the cosine similarity with the layer-16 direction, and mean proj is the average projection of each group onto the direction.

Why

The difference of means is the simplest way to turn two sets of examples into a direction: everything the two sets share cancels, and what is left points from “answered” toward “refused” (adapt-representation). This is the risk this lab is about. A shared additive channel means one vector of 576 numbers, measured from 84 harmless prompts with read-only hooks, reads a policy decision and is a candidate handle for changing it (adapt-abliteration). Layer 16 is used from here on. It sits where Step 2 shows the decision forming, and it was picked while the lab was built; how strongly the write works depends on the layer, which the first Going Further exercise measures. Its direction still has cosine 0.67 with layer 18’s, and later layers drift further from it. Caveat: the two contrast sets differ in topic as well as outcome (vault requests against unrelated questions), so d_16 carries “about the vault” as well as “refuse”. A cleaner contrast would compare refused and answered requests on the same topic.

What to notice: subtracting the vector once drops refusals from 20/20 to 7/20 and five replies print the vault code (the remaining 8 answer without the code, often inventing one), adding it makes the guard refuse 14 of 16 harmless questions, and projecting it out of every layer still refuses 19 of 20 vault requests and now refuses all 16 benign questions too.

Why

Layer 16 means the stream after 16 blocks, which is the output of the block Python numbers 15 (it counts from 0); that is why the hook sits on model.layers.15 and Step 5 edits model.layers.15. The hook adds a constant vector to the stream there at every position, which moves the average refused prompt’s stream at the last prompt token to where the average answered prompt sits; that is activation steering in its simplest form, used in both directions (adapt-steering, attack-steering-misuse). Directional ablation sets the component along the direction to zero everywhere (adapt-abliteration); it worked in the larger chat models of the cited paper, but here both groups sit on the negative side (Step 3), so zeroing pushes benign prompts toward “refuse”. The cost of the working write shows in the last column: only 4 of 16 benign replies stay word for word the same, and the weights hash exactly as before, so a file check cannot see any of it.

Why

The orthogonalized checkpoints of adapt-abliteration instead change existing matrices and keep the tensor list, and either kind of copy carries the change to everyone who loads it (attack-refusal-ablation, and LAB-39 for why weight changes persist).

Why

A manifest with one sha256 per tensor plus the architecture fields of the config, recorded when the model was released, is the checkpoint half of defense-provenance; unlike a single file hash it says what changed, here every o_proj, every down_proj and the embedding for the orthogonalized copy, and one extra bias for the fold (LAB-27 builds the same kind of map). The orthogonalized copy is built in memory as the weight form of Step 4’s projection and is only hashed, never run. Limitation: the hook lives in the process and leaves every tensor untouched, so the manifest passes it; the runtime audit of LAB-39 Step D2 and the gate below are the checks for that case.

What to notice: the clean reload reproduces all 36 baseline replies and passes, while each of the three changed models fails on at least two of the four rules, including the added vector that never touches the vault requests.

Why

defense-regression re-runs held-out safety and utility tests after every model change and compares them with a trusted baseline, here the guard’s replies recorded in Step 4. The policy rules (refusals, no canary) catch the subtracted direction, and the utility rules (benign refusals, unchanged replies) catch the added one. A hook only exists inside a process, so the gate sees one only when it runs inside the serving process; who may attach hooks there is the A07 question, as file write access is for A09 (concept-parameters). Limitation: 36 fixed prompts can miss a change that only fires on a trigger, and a model tuned to pass these exact probes would pass them.
